title: "Routing"
summary: "Which Go file answers which route, and how Kit's route files map onto Go."
---

SKGo keeps SvelteKit's [filesystem router](https://svelte.dev/docs/kit/routing) as it is. `src/routes` is the root route, `src/routes/about` is `/about`, `src/routes/blog/[slug]` has a `slug` parameter, and the `+` files mean what they mean in Kit. What changes is where the server half of a route is written: in Go, in the same directory, under a fixed file name.

| Kit's file          | What you write          | Declared with                                               |
| ------------------- | ----------------------- | ----------------------------------------------------------- |
| `+page.server.ts`   | `page.server.go`        | `skgo.Load`, `skgo.Action` and the other action markers     |
| `+layout.server.ts` | `layout.server.go`      | `skgo.Load`                                                 |
| `+server.ts`        | `server.go`             | `skgo.GET`, `skgo.POST`, …, `skgo.QUERY`, `skgo.Fallback`   |
| `*.remote.ts`       | `*.remote.go`           | `skgo.Query`, `Command`, `Form`, `LiveQuery`, `BatchQuery`, `Prerender` |

[`skgo generate`](/docs/cli/generate) reads the Go files and writes the Kit file next to each one, with a body that throws. Kit builds its router and its client from those files; at request time the Go function is what answers. `+page.svelte`, `+layout.svelte`, `+error.svelte`, `+page.ts` and `+layout.ts` stay yours and stay TypeScript.

## +page

### +page.svelte

Unchanged. A page receives `data` from the loads above it and `form` from the last action, typed through `./$types` as in Kit; the types come from the Go structs your loads and actions return.

### page.server.go

A `page.server.go` holds the page's server load and its form actions. The load is a function that takes the generated `PageRequestEvent` and returns a struct:

```go
/// file: src/routes/invoices/page.server.go
package invoices

import (
	"github.com/tylergannon/skgo"
)

type Invoice struct {
	Number           string `json:"number"`
	DueDate          string `json:"dueDate"`
	OutstandingCents int    `json:"outstandingCents"`
}

type PageData struct {
	AsOf     string    `json:"asOf"`
	Invoices []Invoice `json:"invoices"`
}

func pageLoad(event PageRequestEvent) (PageData, error) {
	return PageData{
		AsOf: "2026-09-28",
		Invoices: []Invoice{
			{Number: "INV-300", DueDate: "2026-10-15", OutstandingCents: 7400},
			{Number: "INV-100", DueDate: "2026-09-10", OutstandingCents: 12500},
			{Number: "INV-200", DueDate: "2026-09-05", OutstandingCents: 0},
		},
	}, nil
}

var _ = skgo.Load(pageLoad)
```

`skgo generate` writes the `+page.server.ts` Kit compiles from it:

```ts
/// file: src/routes/invoices/+page.server.ts
// Code generated by skgo. DO NOT EDIT.
import type { RequestEvent } from "@sveltejs/kit";

export const load = async (event: RequestEvent): Promise<{ asOf: string; invoices: Array<Invoice> }> => {
  throw new Error("skgo: implemented in Go");
};
```

[Loading data](load) covers the load's inputs and what it may return; [Form actions](form-actions) covers the actions a `page.server.go` can declare beside it.

### +page.ts

Unchanged. A universal load runs in the browser as well as on the server, so it stays TypeScript, and so do the [page options](page-options) `prerender`, `entries`, `ssr`, `csr`, `trailingSlash` and `config`. When a route has both, the Go load runs first and its result is the universal load's `data` argument, exactly as with a `+page.server.ts`.

## +error

Unchanged. When a Go load returns an error, Kit renders the nearest `+error.svelte` with the status and message the Go function chose, walking up the tree the way it does for a thrown `error(...)`; see [Errors](load#Errors). As in Kit, `+error.svelte` is not used for an error from a `server.go` handler or from the `handle` hook.

## +layout

### +layout.svelte

Unchanged.

### layout.server.go

A `layout.server.go` holds the layout's server load, declared with the same `skgo.Load` marker; the file name is what makes it a layout load. Its data reaches every page below it:

```go
/// file: src/routes/account/layout.server.go
// layoutLoad is the section's guard and its shared data.
//
// The session comes from the request's locals, which the app's one `handle`
// hook filled in; nothing here reads a cookie or knows how a session is
// spelled. Turning a signed-out visitor away here turns them away from every
// page below, so adding another one needs no new guard.
func layoutLoad(event LayoutRequestEvent) (LayoutData, error) {
	ctx := event.Context()
	session := app.LocalsFrom(ctx).Session
	if session.User == "" {
		return LayoutData{}, &skgo.Redirect{Status: 307, Location: "/"}
	}

	// The visitor can ask for this section's data again without navigating;
	// `invalidate('app:account')` in the browser is what makes kit's client ask
	// for this node and no other.
	event.Depends("app:account")

	return LayoutData{
		AccountUser:   session.User,
		AccountSerial: nextSerial(ctx),
	}, nil
}

var _ = skgo.Load(layoutLoad)
```

A route directory is one Go package, so a `page.server.go` and a `layout.server.go` in the same directory cannot both name their function `load`. Call them `pageLoad` and `layoutLoad`, or anything else; the file a marker is in decides which Kit file it generates.

## +server

A `server.go` is Kit's [`+server.ts`](https://svelte.dev/docs/kit/routing#server): a route that answers with whatever response it writes. Each handler is an ordinary `http.HandlerFunc`, and the marker names the method it answers:

```go
/// file: src/routes/api/todos/server.go
// list answers `GET /api/todos` with the todos this visitor may see.
//
// Who the visitor is comes from the app's Handle hook, exactly as it does in a
// load or a remote function: the endpoint reads the session it stored rather
// than parsing the cookie again.
func list(w http.ResponseWriter, r *http.Request) {
	session := app.LocalsFrom(r.Context()).Session
	writeJSON(w, http.StatusOK, visitor.Store(r.Context()).Todos(session.User != ""))
}
```

```go
/// file: src/routes/api/todos/server.go
var (
	_ = skgo.GET(list)
	_ = skgo.POST(add)
	_ = skgo.QUERY(search)
)
```

`skgo.GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`, `HEAD` and `QUERY` are available, one per method, and the generated `+server.ts` exports the same names so Kit knows which methods the route answers. The status, headers and body are the handler's own; SKGo neither encodes nor interprets them, which is what makes the route usable by `curl`, a mobile app or a webhook as well as by your pages. Kit's rule that a `HEAD` request is answered by the `GET` handler holds.

### Receiving data

Read the body as in any Go handler: `json.NewDecoder(r.Body)`, `r.ParseForm`, or `io.ReadAll`. The request's context carries the same locals your loads see, through `app.LocalsFrom(r.Context())`, and the event through `skgo.EventFrom(r.Context())`; see [Go and web standards](go-standards#net-http-Beyond-the-standard-library).

### Fallback method handler

`skgo.Fallback(fn)` is Kit's `fallback` export: `fn` answers every method the route declares no handler for, including methods such as `MOVE` that have no marker of their own. As in Kit, `HEAD` prefers the `GET` handler over the fallback.

### Content negotiation

A `server.go` may sit beside a `page.server.go`, and Kit's rules decide which answers: `PUT`, `PATCH`, `DELETE`, `OPTIONS` and `QUERY` always reach the endpoint, and `GET`, `POST` and `HEAD` reach the page when the `accept` header prefers `text/html`, the endpoint otherwise. The example's `/actions` route has both:

```go
/// file: src/routes/actions/server.go
package actions

import (
	"encoding/json"
	"net/http"

	"github.com/tylergannon/skgo"
)

// This sibling +server route answers a POST only when Kit selects the endpoint.
func endpointPost(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(map[string]string{"answer": "Endpoint POST answered by Go"})
}

var _ = skgo.POST(endpointPost)
```

`+layout` files have no effect on a `server.go`. Logic that must run before every request belongs in the `handle` hook.

## Route parameters

A dynamic segment reaches a Go load as a typed accessor on `event.Params`, named after the segment: `event.Params.Slug()` for `[slug]`, `event.Params.ID()` for `[id]`, `event.Params.Rest()` for `[...rest]`. Reading one records a dependency, so the load reruns when that segment changes and not otherwise; see [Rerunning load functions](load#Rerunning-load-functions). In a remote function or an action, the current value is `skgo.EventFrom(ctx).Param("slug")`.

SvelteKit spells route directories `[id]`, `(marketing)` and `[...rest]`, which Go cannot import. You put your Go in that directory anyway:

```go
/// file: src/routes/items/[id]/item.remote.go
// Package item serves the /items/[id] route. It sits in the route directory
// SvelteKit named, brackets and all: the generator gives it an import path Go
// can spell, so nothing about the layout has to bend around Go.
package item

import (
	"context"
	"fmt"

	"github.com/tylergannon/skgo"
)

// Item is one thing in the catalogue.
type Item struct {
	// ID is the value SvelteKit matched into the `[id]` segment.
	ID string `json:"id"`
	// Name is what the page shows.
	Name string `json:"name"`
	// Colocated says where the Go that answered lives, so the page can show
	// that a bracketed directory really is the source of the answer.
	Colocated string `json:"colocated"`
}

func getItem(ctx context.Context, id string) (Item, error) {
	if id == "" {
		return Item{}, skgo.Errorf(400, "An item needs an id")
	}
	return Item{
		ID:        id,
		Name:      fmt.Sprintf("Widget %s", id),
		Colocated: "src/routes/items/[id]/item.remote.go",
	}, nil
}

var _ = skgo.Query(getItem)
```

`skgo generate` gives each such package an import path Go can spell, under `internal/skgo/links/`, and the generated bindings use it. Your own code needs that path only when one route package calls another:

```go
/// file: src/lib/auth.remote.go
import (
	"context"

	"github.com/tylergannon/skgo"
	"github.com/tylergannon/skgo/example/businesslogic"
	"github.com/tylergannon/skgo/example/internal/skgo/params"

	// The sign-in form lives in the root layout, so signing in changes what
	// the todos page is showing — and a command runs only the queries it
	// names. SvelteKit spells route directories `[id]` and `(marketing)`,
	// which Go cannot, so skgo puts the route tree behind its own module
	// boundary and gives each route package a Go-nameable address under
	// generated/links. That address is the only way to reach one, and it is
	// base32 of the directory: this one is "src/routes/todos".
	todos "github.com/tylergannon/skgo/example/internal/skgo/links/onzggl3sn52xizltf52g6zdpom"
)
```

### Matching

A [param matcher](https://svelte.dev/docs/kit/advanced-routing#Matching) has two halves. Kit's half is `src/params.ts`, as in any Kit project:

```ts
/// file: src/params.ts
import { defineParams } from "@sveltejs/kit/params";

export const params = defineParams({
  Order: (value: string) => {
    if (!/^[+-]?\d+$/.test(value)) return;
    const parsed = Number(value);
    if (parsed < 0 || parsed > 1000000) return;
    return parsed;
  },
});
```

The Go half is a function of the same name in `src/params.go`, returning the typed value and whether it matched:

```go
/// file: src/params.go
package hooks

import (
	"fmt"
	"strconv"
)

// OrderNumber keeps its identity and methods in a generated load event.
type OrderNumber int64

func (n OrderNumber) Label() string { return fmt.Sprintf("Order #%d", n) }

// Order is paired with the declared Order matcher in params.ts.
func Order(value string) (OrderNumber, bool) {
	n, err := strconv.ParseInt(value, 10, 64)
	return OrderNumber(n), err == nil && n >= 0 && n <= 1000000
}
```

A load under `[number=Order]` then receives the Go type, methods and all:

```go
/// file: src/routes/typed-load/[number=Order]/page.server.go
package typedload

import "github.com/tylergannon/skgo"

type PageData struct {
	Label string `json:"label"`
}

func load(event PageRequestEvent) (PageData, error) {
	return PageData{Label: event.Params.Number().Label()}, nil
}

var _ = skgo.Load(load)
```

The Go server runs the Go matcher when it routes a request, and Kit's client runs the TypeScript one when it navigates; keep the two in agreement.

### Optional parameters in layouts

A layout above `[section]/[item]` sees `item` only on some of the pages below it, so the generated `LayoutParams` accessor for a segment that is not in every descendant returns a pointer, nil when the current page has no such segment. A page's `RouteParams` accessors return the value itself.

## Go packages

Every route directory with Go files is one Go package, named whatever you like. Besides the four recognised file names, any other `.go` file in the directory is part of the package: helpers, types and tests live beside the handlers that use them, as Kit lets you colocate components and modules. `skgo_gen.go` is generated and declares the directory's `PageRequestEvent` or `LayoutRequestEvent` and its typed parameters; [Project structure](project-structure#Generated-files) lists everything the generator writes.

## $types

Unchanged on the Svelte side: `PageProps`, `LayoutProps`, `PageData` and `ActionData` come from `./$types` as in Kit, and the generated `+page.server.ts` is what gives them their shape, so `data` in a page is typed from the struct the Go load returns. On the Go side, the generated `PageRequestEvent` and `LayoutRequestEvent` play the role `PageServerLoad` and `LayoutServerLoad` play in Kit: they are what tells the compiler what `event.Params` holds.
