# #203: Support migration between TypeScript and JavaScript generation

https://github.com/tylergannon/skgo/issues/203
State: open

## Issue body

## Feature request

Support changing an **existing** skgo application from TypeScript to JavaScript/JSDoc, and back, as a deliberate migration. The JavaScript generation feature only needs to honor the language chosen when the app is created; migration between languages is separate work.

## Desired behavior

- After the developer changes the app's `tsconfig.json`/`jsconfig.json` choice and regenerates, skgo writes the frontend modules in the selected language and updates remote IDs and manifest paths to match Kit's source paths.
- Obsolete skgo and Polytype output from the previous language is removed across remote functions, named wire types, server loads/actions, and endpoints. Authored files and files signed by another generator survive.
- A second migration back to the original language produces a usable application. No claim of byte-for-byte TypeScript output is necessary; both generated forms must type-check and run.

## Definition of done

1. A fixture with remote functions, named types, a Go load/action and a Go endpoint completes TS→JS→TS generation through the normal command. Each stage has no stale generated modules of the other language, and authored files are preserved.
2. At each stage, Kit's checker accepts correct consumer calls and rejects an intentionally wrong one; the frontend builds with the matching manifest and remote hash.
3. A Go-owned remote and server-data response remains reachable after each migration through the real handler and Kit client. Existing TypeScript and fresh JavaScript creation remain unaffected.

This issue is deferred from the initial JavaScript/JSDoc generation work; do not make its round-trip acceptance a gate for that feature.
