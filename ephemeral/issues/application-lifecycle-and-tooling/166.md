# #166: Expose Kit handleValidationError behavior for Go remotes

https://github.com/tylergannon/skgo/issues/166
State: open

## Issue body

## Desired result

An application should be able to customize validation failures with the behavior Kit provides through `handleValidationError`.

## Acceptance

A deliberately invalid remote argument produces the application’s chosen public validation result without invoking the Go function, in development and production.

## Current boundary

The matrix has no Go `handleValidationError` equivalent.

Feature matrix: https://tylergannon.github.io/skgo/features.html. Kit’s pinned source and client behavior define compatibility.

### Currentness and executable questions

Installed `example/web/node_modules/@sveltejs/kit/package.json` is **3.1.0**, verified in this worktree. Its `src/runtime/server/errors.js:22-73` and `src/exports/hooks/public.d.ts:24-70` retain the same validation-kind, private-issues, partial-public-result behavior as the cached 3.0.0 sources. Installed source remains authoritative; cached examples are contextual.

- **Does skgo already have a suitable public-result hook?** Partly: `HandleError` already returns `map[string]any` and supports custom fields plus status/message overrides (`handle_error.go`). But `CaughtError` currently documents/constructs only `app` and `unknown`, has no issues field, and `RemoteConfig` has no hook. Existing page handling is not remote validation handling. This is a bounded capability gap, not a need to invent a second public hook.
- **Is development already equivalent?** No proof yet. `dev_remote.go` currently routes native callback failures through the load error hook and emits an already-shaped body; it does not by itself identify validation failures or establish that production remotes use the same public result. The builder must qualify both actual development and production paths against pinned Kit and preserve full custom App.Error fields without double handling.
- **What proves the goal?** Independent literal invalid argument fixtures must show the app-chosen public body, safe defaults when no override is returned, private issue availability to the hook, and a remote-body invocation count of zero. Cover the real production handler and development callback/front door; only add browser scenarios for claims that need Kit's client to act. Existing decoder/body-refusal assertions are regressions to preserve, not substitutes for hook proof.
- **HITL decision needed?** None identified. Kit answers the API semantics; the issue already states the goal and development/production acceptance. Ready for implementation once the builder maps the installed 3.1.0 call sites and chooses an idiomatic Go representation within those semantics. Broadening all unrelated error-kind behavior is outside this issue.
