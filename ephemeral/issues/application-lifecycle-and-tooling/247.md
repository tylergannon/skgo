# #247: Isolate build-test fixtures and share expensive setup without weakening contracts

https://github.com/tylergannon/skgo/issues/247
State: open

## Issue body

## Problem

Narrow generator and prerender contracts currently depend on unrelated parts of the example application. Some tests copy the whole example, modify one behavior, and then generate or build every copied consumer. A valid change elsewhere in the demo can stop these tests before they reach their intended assertions.

During the typed remote-parameter work, four tests failed compiling a new contact callback that referenced a generated named-type variant:

- `TestPrerenderGoLoadFailureNamesAuthoredRoute` (`internal/gen/prerender_test.go`).
- `TestGoPagePrerenderRedirectBuildsKitsNativeArtifact` (`internal/gen/prerender_redirect_test.go`).
- `TestCompiledProductionNoArgumentNullReachesTheArtifactLookup` (`internal/gen/prerender_remote_ssr_test.go`).
- `TestTypedLoadParamsRefreshBeforeStaleHandlerCompilation` (`internal/gen/load_params_test.go`).

The prerender fixtures rename `web` to `ui`, changing the matcher package path; the type-refresh fixture changes `OrderNumber` to the named struct `RevisedOrder`. Generated variants distinguish Go package/type identity, so those transformations exposed an unrelated hard-coded contact consumer. These were compilation failures before the intended prerender or repaired-handler assertions, not four independently demonstrated prerender defects.

The transformations have legitimate contracts. The unnecessary dependency on contact forms does not.

This is not a claim that every test builds everything separately. `internal/gen/main_test.go` already builds the CLI once with `sync.OnceValues` and uses package-lifetime temporary storage. `internal/gen/evolution_test.go` batches compatible edits into shared generation results. `example/typedrift_test.go` shares setup for distinct baseline, regenerated and deliberately drifted source states. Extend those mechanisms rather than replacing them with a new runner.

## Desired result

Changes should be quick and dependable to verify. A narrow test should fail for its own contract, give clear feedback, and avoid unnecessary generation, builds and server starts. Real runtime integration and real user behavior must remain covered.

## Proposed scope

Start with the copied-example generator/prerender cases above and the closely related `sharedFixture` in `internal/gen/shared_params_test.go`. Inspect `internal/adapter/prerender_inputs_build_test.go` for compatible build grouping. Do not turn this into an unrelated wholesale suite rewrite.

Use purpose-built, checked-in applications under `testdata` or the repository's chosen fixture convention. Include only the routes, handlers, matchers and configuration needed for the contract. Where the claim depends on generation, Kit's build, the adapter or production rendering, use the actual SKGo implementation, pinned Kit and current adapter. Avoiding mocks comes from those real components, not from copying the entire demo. Temporary staging for mutation and output isolation remains appropriate, prepared once per compatible group.

Group tests by compatible source/build configuration. Generate and build once per group per package invocation, reuse immutable artifacts, and share a server only where HTTP assertions require one. Reset request/application state between assertions; do not share mutable state in ways that introduce ordering or parallelism dependencies. Ordinary HTTP contracts should use Go `httptest` and in-process real handlers when neither a browser nor a fresh compiled application is required. Preserve the actual production composition wherever composition is the claim.

Keep deliberately incompatible source/configuration transitions separate:

- Named-type evolution: change the matcher to `RevisedOrder`, demonstrate generated declarations refresh before the old handler fails, repair its method calls, and serve independently specified literal values through the real handler.
- A nondefault frontend root: explicitly prove generation and the required build/runtime behavior from `ui`, rather than attaching a rename to every unrelated assertion.
- Expected build failures and artifact mutations: preserve their diagnostic or lookup contracts with isolated state and the genuinely necessary rebuilds.

Retain limited whole-example coverage for application composition and the existing production/development browser requirements. Browser assertions remain where Kit's client or a usable JavaScript-off submission is part of the claim. During iteration, run the affected groups; run full browser suites at meaningful stabilized checkpoints, avoiding duplicate broad validation while another session changes the same source.

Use existing Go tests, package setup and ordinary commands. No bespoke proof runner, new framework, persistent artifact cache or command that claims the software is done. Explicit predictable toolchain and server-log setup is useful; this issue does not expand into fixing all tooling infrastructure.

## Acceptance

- Record a baseline and an after comparison using consistent settings and cache conditions: generator invocations, builds, server starts, elapsed time and relevant CPU/memory impact. Report measured results; do not invent a speed threshold or promise savings from test counts alone.
- Each compatible group performs expensive preparation once per invocation. Separate setups are justified by incompatible configurations or intentional state transitions.
- Assertions are independently runnable and order-independent; running selected tests and the full group exercises the same setup and contracts. Shared state cannot leak between cases.
- Preserve the named contracts above, real implementation paths, original Go types/methods, literal expected receipts, source-root coverage and type-refresh failure/recovery behavior. Do not derive expected answers from generated output.
- Demonstrate that an unrelated demo change no longer introduces unrelated consumer compilation into the narrow fixtures. Retain whole-example coverage that still catches actual demo integration failures.
- Relevant Go and required production/development browser suites pass without skipped checks or weakened assertions. Establish that the retained assertions fail when their covered behavior is broken.

## Related work and limits

Related: #136 moves HTTP-only coverage out of browsers; #183 streamlined form-action validation; #229 repaired generated fixture/type-drift proof after formatting. This proposal addresses fixture dependencies and repeated preparation within Go build/integration testing, rather than duplicating those scopes.

Adapter SIGTERM-drain timeouts and private compile-directory cleanup failures have also been observed. Their cause remains unresolved. This fixture improvement is not claimed to fix them, and unchanged adapter source or a passing isolated retry does not establish a pre-existing failure or resource-contention cause. Diagnose and reconcile those failures independently.

Status: proposed work, not a fulfilled performance or reliability claim.
