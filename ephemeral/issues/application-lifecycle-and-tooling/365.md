# #365: Generate a toolchain version manifest and export the qualified versions

https://github.com/tylergannon/skgo/issues/365
State: open

## Issue body

## Problem

An SKGo app's documentation, about page or Dockerfile has to state the versions the SKGo release qualifies:
- the SKGo version;
- Go;
- Kit;
- VitePlus;
- pnpm;
- the Node range.

Today those values exist only as unexported constants and files:
- `internal/toolchain/pins.go` holds VitePlus and pnpm;
- `internal/kitpatch` has Kit 3.1.0 only inside a patch filename;
- `go.mod` holds the Go version;
- VitePlus's `engines` holds the Node range.

So consumers copy the literals by hand. The skgo-project docs rewrite ended up with about 180 hard-coded version strings across 75 pages, and every release would quietly rot them.

## Proposal

The manifest should be an **input** to the app's build, written by code generation and checked in like the other generated files. It should not be a build result.

1. **Public Go API.** Export the qualified toolchain from one source, for example a `skgo.Toolchain()` function returning a struct with `SKGo`, `Go`, `Kit`, `VitePlus`, `PNPM` and `Node`.
   - `internal/toolchain` keeps owning the pins.
   - Kit and the Go version become pins there too, each with a test that pins it to `go.mod` or the Kit patch it must agree with.
   - The SKGo version comes from build info.
2. **`skgo generate` writes the manifest** beside `src/env.ts` and `src/params.ts`, for example `web/src/skgo.versions.ts` exporting `versions` with the same six keys. It is generated from the same constants, so Go and the frontend cannot disagree.
3. **Adopting a release** is then `go get github.com/tylergannon/skgo@vX && skgo generate`, and the version change appears as a reviewable diff.

The first consumer is the skgo-project docs pipeline. It will substitute `%go%`, `%kit%` and the rest from this manifest, and refuse any page that contains a literal equal to a manifest value.
