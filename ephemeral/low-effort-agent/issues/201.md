# 201: Match Kit HEAD fallback Content-Length behavior

https://github.com/tylergannon/skgo/issues/201

## Gap in the api-routes cell

Pinned Kit 3 (`next.28`) dispatches HEAD to GET when no HEAD handler exists, then returns `new Response(null, response)`, preserving the GET response headers. Its Node response writer ends with no body and does not infer a length for the discarded body. Thus a GET response with no explicit `Content-Length` should yield a HEAD response with no `Content-Length`; an explicit length is preserved.

skgo also dispatches HEAD to GET, but its ordinary Go handler writes directly to `net/http`. Go may infer `Content-Length` from written bytes even though the HEAD body is suppressed. The current `TestHeadIsAnsweredByTheGetHandler` checks status, empty body and content type, but not this header. Reproduce this at the real HTTP server before changing behavior.

## Acceptance

- A real-server test sends HEAD to a GET handler that writes literal `thing` without setting `Content-Length`: status 200, empty body, and no `Content-Length`, matching Kit's fallback.
- A second handler explicitly sets `Content-Length: 5`; HEAD preserves that header with an empty body.
- Keep existing GET, explicit HEAD, method dispatch and streaming behavior intact. If matching Kit requires a substantial response-writer abstraction, report the constraint before widening the implementation.

This belongs in the existing `api-routes` bucket as a new named Go check. The cell set does not change.

### tylergannon — 2026-09-27T03:13:17Z

Real-server reproduction confirmed the HEAD fallback gap: with a GET handler that writes `thing` and does not set `Content-Length`, HEAD returns `Content-Length: 5`; pinned Kit 3 next.28 cancels the response body before its Node writer and sends no inferred length. An explicit `Content-Length: 5` is preserved as expected.

PR #202 tried a small writer wrapper that discards fallback GET writes. A further real-server probe exposed another compatibility edge: a GET handler that calls `WriteHeader(200)` before writing `thing`, without setting `Content-Type`, has `text/plain; charset=utf-8` on GET but loses that inferred type on HEAD under the wrapper. A first-write sniff cannot fix this because net/http snapshots headers at `WriteHeader`. Preserving both headers would require deferring/replaying status and accounting for flush and panic behavior, beyond the narrow change attempted here. PR #202 is closed without merge; issue remains open for a bounded future implementation.
