## Findings

### 1. Issue: the endpoint fix has not been demonstrated through the running application

Issue #128's Definition of Done specifically requires starting the real example app in both modes, sending the same cross-origin form-shaped mutation to a real Go endpoint, observing the endpoint response in development, and observing a pre-handler `403` in production. The implementation adds only a registry-level unit test (`endpoint_test.go:324-339`). The available E2E last-run files show that the existing browser suite passed in both modes, but that suite contains no cross-origin endpoint request and therefore cannot demonstrate the behavior changed here. No request/response transcript or other inspectable artifact for the live `/api/todos` endpoint was found.

Impact: the central runtime claim remains unproven at the composition seam where `example.NewHandler` must actually set `endpointCfg.Dev = true` for the proxied server (`example/server.go:110-145`). The unit test proves `Endpoints` honors a manually populated flag, but it cannot catch the example application failing to propagate that flag or a different outer handler refusing the request. Run the exact dev/prod requests required by the issue against the real server and retain an inspectable result that also proves whether the endpoint ran.

### 2. Issue: the documented focused E2E command cannot pass the new mode gate

The new global setup requires `SKGO_EXPECTED_MODE` (`example/e2e/global-setup.ts:4-7`), and the Just recipe correctly sets it (`Justfile:81-82`). However, the directly documented focused-run command still sets `EXPECTED_MODE=prod` (`ephemeral/index/README.md:120-124`). Following that command now fails in global setup before any selected test runs because `SKGO_EXPECTED_MODE` is absent.

Impact: the implementation leaves one of the repository's concrete E2E operating gestures broken. Change that invocation to use `SKGO_EXPECTED_MODE=prod` so the documented focused proof path agrees with the new independently supplied mode contract.
