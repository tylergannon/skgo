## Findings

### 1. Issue — half the plan targets an API that does not exist on the base it names

**Category:** incomplete requirement / feasibility.

Plan §1 ("Typed-load evolution", "Shared parameter types"), §3 and the §6
"type refresh" break experiment all require generated load params:
`RequestEvent`, `event.Params.Number()`, `skgo_params_gen.go`,
`internal/skgo/params`, `web/src/params.go`, and the `typed-load` /
`typed-dependencies` routes. None of this exists at `b3984d8`:

- `grep loadParamsFile|sharedParamsFile|prepareLoadParams internal/gen/*.go` → no hits on this checkout; on the branch they are `load_params.go:22` and `shared_params.go:16`.
- `example/web/src/params.go` is absent here (only `hooks.go`); no `typed-*` route directories exist under `example/web/src/routes`.
- The contact consumer whose compilation broke the four named tests
  (`contact.remote.go:109`, `params.Variant_ID_BuiltinString`) exists only on
  the branch.

The plan acknowledges the two bases ("reconcile the implementation base with
their eventual integrated state") but gives no ordering. As written, an
implementer on `main` cannot author, compile or run the §3 fixtures, and an
implementer on the branch collides with active, uncommitted work in core files
(`data.go`, `document.go`, `endpoint.go`, `event.go`, …). Either way the "one
deliverable" cannot be demonstrated end to end on any single checkout.

**Impact:** the acceptance in §6 (baseline/after counts, shuffled runs, the
"break a contact consumer" experiment) cannot be executed for half the fixtures
on the only base that is stable, and the plan does not say which half ships
first.

**Required change:** split the work explicitly. Phase A on `main` now: the
prerender-failure fixture, the shared production fixture (redirect + remote
artifact cases), the nondefault `ui` root, and the adapter minimal-app merge.
Phase B after the typed-params branch integrates: typed-load evolution and the
shared-params matrix, authored against the integrated API. State that the §6
"type refresh" experiment belongs to Phase B and the contact-consumer
experiment on `main` uses an ordinary compile break in `contact.remote.go`
rather than the branch-only named-variant case.

### 2. Issue — checked-in fixture modules have no stated way to track the example's dependency pins

**Category:** feasibility / critical antipattern (silent rot).

Every proposed `testdata` application must be a Go module with its own
`go.mod` (`replace github.com/tylergannon/skgo => …`, `tool …/cmd/skgo`, the
`ignore ./ui/node_modules` line that `example/go.mod:7` needs for the embedding
package) **and a `go.sum`** covering skgo's full transitive graph, plus a
`web`/`ui` skeleton (`package.json` with `#lib` imports, `vite.config.ts` with
the adapter and `experimental.remoteFunctions`, `tsconfig.json`, `src/app.html`,
`src/hooks.ts`). The plan proposes three or four such apps and says nothing
about how their pins stay equal to `example/`'s.

The concrete failure: tests run `go generate`/`go test` inside the staged copy
with `GOWORK=off` (`main_test.go:23`, `runGoGenerate`). The first time the root
module bumps a dependency (polytype, goja, x/tools…), every fixture whose
`go.sum` was not also updated fails with `missing go.sum entry` before reaching
its assertion — exactly the "fails before its own contract" symptom the issue
is about, now multiplied by fixture count. Checked-in `vite.config.ts`
duplicates drift the same way when Kit's config shape moves (the SKILL notes
`svelte.config.js` is gone and adapter plugins split `pre`/`post`).

Today `copyExample` avoids this by copying the example's live `go.mod`/`go.sum`
and rewriting only the replace path (`stalegen_test.go:170,249`).

**Required change:** decide, in the plan, the single source of truth. The
least-rot option: fixtures check in only what is contract-bearing (routes,
handlers, matchers, `server.go`, `cmd/main.go`, embed package); staging
composes the module by copying `example/go.mod` + `example/go.sum` and the
example's `web/{package.json,vite.config.ts,tsconfig.json,src/app.html}` into
the fixture, rewriting the replace path and `--web` root as the existing
helpers already do. If instead each fixture commits its own pins, name the test
that fails loudly when they diverge from `example/` (a byte comparison is
enough) so divergence is a red test, not a mystery.

### 3. Issue — "separately selectable" remote-artifact assertions share a process-global middleware slot

**Category:** race / ordering dependence introduced by the plan.

§2 says the remote assertions (500 missing-key, 409 stored error, transform
fallback) become separately selectable tests over one immutable build with
"fresh handler state". The transform case works by assigning a package-level
variable in the fixture app and composing it into every handler:
`prerender_remote_ssr_test.go:58` declares `var PrerenderTransformFixture
skgo.Middleware`, the child test assigns it at `:255`, and `server.go`'s
`Sequence(...)` includes it for *all* handlers built afterwards. Today this is
safe only because the three cases run sequentially inside one test function.

Split into three `t.Parallel`-eligible tests in the child package, the
transform test's assignment races with the 500/409 tests' `NewHandler` calls
and, depending on schedule, the 500/409 handlers resolve through a
one-shot-failing transform. The 409 test would then see a 500 and the plan's
"shared state cannot leak between cases" acceptance is violated by the design
itself. `-shuffle=on` (which §6 mandates) makes this intermittent rather than
reproducible.

**Required change:** the fixture must inject the transform per handler (an
option on the fixture's `NewHandler`, or a handler constructor that takes the
middleware), never through a package variable; and the child-package tests
must not share any counter whose expected value depends on which test ran
first. The `Calls()` atomic is fine only because every case expects zero —
say so, and keep it that way.

### 4. Nitpick — a second checked-in app for one three-line edit

**Category:** over-engineering.

§1 proposes a distinct "prerender failure" application whose only difference
from the successful production fixture is a root `layout.server.go` returning
`prerender fixture literal failure`. The plan's own rule is "staged into
temporary directories when tests require mutation", and the existing test
already installs the failure by a guarded `strings.Replace`
(`prerender_test.go:52-62`). A second app duplicates the whole module/frontend
skeleton (and doubles finding 2). Prefer: one production fixture with a root Go
layout load; the failure test stages it and plants the literal error with a
must-match guard, as today. Expected build output (`route ID /about`, `path
/about`, `source src/routes/layout.server.go`, `GET /about`) still holds
provided `/about` is the only prerendered route under that layout *or* the
assertion accepts whichever prerendered route Kit reports first — state which.

### 5. Nitpick — be explicit about what still copies the whole demo

**Category:** incomplete scope statement.

After the plan, these still copy `example/` wholesale and keep the fragility
the issue describes: `TestTypedLoadMatchersPrerenderNamedGoValues`
(`load_params_test.go:158`), `TestTypedLoadActualParameterDependencies`
(`:200`), `TestSharedParamsFrontendOnlyApplication`
(`shared_params_test.go:425`), the adapter declared-inputs test
(`prerender_inputs_build_test.go:25`, which also edits `about/about.remote.go`
and depends on `businesslogic.Money`), `prerender_inputs_identifier_build_test`,
`undeclared_remote_id_build_test`, the lifecycle tests, and — by design —
`evolved`/`regenerated` (`evolution_test.go:116,186`) and the example module's
typedrift sandboxes, which intentionally assert on the demo's committed output.
§5's "already shares its successful build" is true but answers a different
question than the issue's. List these as retained-as-is with the reason, so the
§6 claim "an unrelated demo change no longer breaks the narrow fixtures" is
scoped to the fixtures that were actually isolated. Also count the child
`go test` compiles (each embeds the whole `build/` via `//go:embed all:build`)
and `svelte-check` runs as builds in the §6 baseline/after comparison; they are
the expensive steps that remain.

## Things checked that are not findings

- §2 compatibility claim verified: both prerender tests use the `ui` root,
  `ORIGIN=http://127.0.0.1:8080`, and a plain `vp build`; the redirect
  assertions are containment checks and the remote-SSR routes add no
  `noargValue` artifact or `/ordinary` prerender, so one build serves both.
- §5 merge verified: the `3215r6/empty` artifact hash is per-module and the
  receipt file is written only by the `empty` module, so alpha/beta can share
  the build without changing either literal.
- Moving the 409 case from on-disk mutation (`prerender_remote_ssr_test.go:159`)
  to an `fs.FS` overlay is consistent with the issue ("isolated state and the
  genuinely necessary rebuilds"); the lookup path is unchanged and the native
  error-artifact shape is proven separately in the adapter declared-inputs test.
- `testdata` directories are skipped by `./...`, so nested fixture modules do
  not affect `just vet`/`just test` at the root; `example/web/src/routes/go.mod`
  shows the repository already relies on nested module boundaries.
- The plan correctly refuses a proof runner, a cache and a speed target, and
  keeps the missing-`node_modules` case a hard failure rather than a skip.
