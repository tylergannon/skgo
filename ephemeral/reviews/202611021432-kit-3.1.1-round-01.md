## Findings

### 1. Issue — patch cleanup can silently delete application-authored changes

**Evidence:** `internal/kitpatch/kitpatch.go:195-200,425-430,554-581`; `internal/update/frontend.go:138-140,328-333`.

The new supersession rule identifies an earlier correction solely from its configuration key and filename. For example, `@sveltejs/kit@3.1.0: patches/skgo-kit-3.1.0-queue.patch` is classified as owned regardless of the file's contents. `Configure` then removes that entry, and `removeOrphanOwnedPatches` deletes the file without reading it. The same cleanup also deletes any unreferenced regular file matching `skgo-kit-*-queue.patch`, including an application's saved or modified copy. The updater subsequently deletes matching files absent from its stage using an even broader `skgo-kit-*.patch` predicate.

This conflicts with the mission's preservation of application changes and the journal's promise to refuse foreign Kit patches (`SVELTEKIT_COMPATIBILITY.md:77-81`). The current-version destination correctly refuses different bytes; the newly permitted earlier-version path has no equivalent ownership check. A filename establishes the intended location, not that its current contents are still skgo's correction.

**Concrete reproduction by source trace:** take a 3.1.0 consumer with the canonical patch entry, add an application-specific fix to `patches/skgo-kit-3.1.0-queue.patch`, and run this checkout's `kit-patch --apply`. The entry satisfies the superseded predicate, bypasses the foreign-patch refusal, is removed from the map, and its file reaches `os.Remove`. There is no content check on that path. The application-specific fix is discarded and the subsequent install uses only the stock skgo 3.1.1 correction. An unreferenced backup such as `patches/skgo-kit-backup-queue.patch` is deleted by the directory sweep even if it was never configured. I did not execute this destructive reproduction against the retained consumers.

**Needed correction:** prove that a superseded file contains a known skgo correction before removing its entry or deleting it; refuse or preserve modified/unknown bytes. Limit deletion to verified superseded artifacts rather than sweeping files by name. Cover an edited earlier patch and an unrelated matching backup, including the updater stage/application boundary. The new successful-upgrade tests cover an unchanged earlier patch and `mine.patch`, so they do not catch this loss.

### 2. Issue — the native-shell example pairs Kit 3.1.1 with an adapter requiring 3.1.0

**Evidence:** `plugins/native-shell/example/web/package.json:4-5`; `plugins/native-shell/example/web/pnpm-lock.yaml:524-528`.

This change advances the native-shell example's Kit dependency and patch to 3.1.1 but retains published `@skgo/sveltekit-adapter@0.40.1`. Its exact peer is still Kit 3.1.0, as both the committed lockfile and installed package manifest show. That adapter also ships only the 3.1.0 correction metadata. The main and CLI examples use the checkout adapter and do not have this mismatch.

**Executed reproduction:** from `plugins/native-shell/example/web`, import the installed adapter's `skgo-adapter/dev.js`, set `SKGO_DEV_DIR` and `SKGO_DEV_ORIGIN`, and call `development({config: {paths: {}}})`. It rejects before startup with:

```text
skgo development requires @sveltejs/kit@3.1.0, installed 3.1.1.
```

I ran this directly with Node without changing files. Thus this is an enforced compatibility failure, not merely an install warning. It violates coherent adoption across the supported examples; an install completing does not qualify the pairing. The retained 3.1.0 adapter also rejects 3.1.1 when its declared-Inputs queue guard is exercised.

**Needed correction:** align this example with the adapter that actually supports 3.1.1, regenerate its lockfile and demonstrate development startup with the intended pairing. Keep the exact-version gate intact.
