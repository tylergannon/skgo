## Finding

### 1. Issue — a failure after successful rendering still discards the production prerender cache

**Missed requirement:** original hydration `p` keys and values must survive the same production error-document recovery that native Kit performs. Fixing only an error escaping `renderPlan` does not cover a successful built-artifact render whose document transform fails.

**Source cause:** `deliver` preserves `answers` on `renderPlan` failure at `document.go:1099–1101`. After a successful render, however, it assembles the document and invokes `TransformPageChunk` at lines **1116–1118**, then still calls **`s.failed(...)` without those answers at line 1121**. `failed` invokes `respondWithError` with no prior map. The recovered error document therefore loses every built prerender answered before this later failure. The new production/nonempty-`p` guard exists but is bypassed at this boundary.

Native `runtime/server/page/render.js:618–621` awaits `transformPageChunk` inside page rendering. `runtime/server/page/index.js:348–361` catches a failure and passes the **same state** to `respond_with_error`; that error render consequently serializes the already settled prerender cache through `collect_remote_data`. This is not a generic development/query error-plane redesign: the counterexample uses the newly supported production built-artifact path and the same existing public transform option.
