## Findings

### 1. Issue: the dev-mode proof cannot show what it is offered as proof of

`issue107-scaffold-dev/home.png` is byte-for-byte identical to `issue107-scaffold-prod/home.png`, and likewise for the two `endpoint.png` frames. That is consistent with a correctly working dev server (the same DOM in the same Chromium gives the same pixels), but it also means the frames carry zero information about the property the issue asks for: "Dev mode answers page documents through `NewDevSSR`/`NewDevPages` and intercepts the Go endpoint before Vite". A browser screenshot of `/` looks the same whether Go rendered the document or Vite served kit's dev shell and the browser rendered it client-side; a screenshot of `/api/probe` shows the same text whether Go answered with 202 or something else echoed the body. `CLAUDE.md` asks for a screenshot "showing the actual state the scenario claims, legible enough to tell whether it is real"; for the dev-mode claims, the state that matters is in the response (Go-rendered markup with `Served by go1.…` and the greeting count already in it, status 202, `Content-Type: text/x-skgo-probe`, `X-Skgo-Handler: Go endpoint`), and none of that is visible in the frames. The `curl -D` the producing session ran against the dev server captured exactly the right evidence, but its output was written to `/tmp` and not kept with the proof. Impact: a human handed these four frames cannot distinguish the fixed dev stack from the pre-fix `NewDevProxy` one the issue reports. The scaffold test does assert all of this (`scaffold_test.go:295-306`, `assertEndpoint`), so the behaviour is verified by test; it is the human-checkable artifact that is missing. A captured `view-source`/response-header frame per mode, or the saved curl transcript beside the PNGs, would close it.

### 2. Issue: "released" has not happened, and main has moved under the branch

The HITL direction restated by the caller was to implement and release. As of this review: no PR for `codex/issue-107`, the commit is not on `origin/main`, and the newest tag `v0.2.3` was cut from #108 without it. The branch merges cleanly onto `origin/main` and #108 touches disjoint files, so this is a sequencing gap rather than a conflict, but the current tree has not been built or tested on top of `8910d3a`: #108 changed `internal/adapter/skgo-adapter.js` and `env.js`, and the scaffolded project consumes the adapter from the tagged release its `go.mod` pins (the test refuses any replace back to the checkout), so a rebase followed by one more `go test ./internal/newapp` run is the minimum before a tag. Also note that a scaffold generated today with the default `-skgo-version` will pin the latest release, which is now `v0.2.3`, while the proof project was generated against `v0.2.2`. Impact: the acceptance is not met until the change is on `main` and in a tag a `skgo new` user can receive.

### 4. Nitpick: a scaffolded app that adds a `transport` hook has no wiring path documented

Unchanged from round 01 finding 4. `example/server.go:183-184` sets `remoteCfg.Transport`/`loadCfg.Transport` from `generated.Transport()`, which only exists when `src/hooks.ts` declares a transport (`internal/gen/emit.go:634-638`), so the template rightly omits it; but `README.md.tmpl` does not say so, and a user who adds the hook gets a generated `Transport()` the server never mounts. One sentence in the README naming the two config fields would close it.

### 5. Nitpick: the four scaffold frames live under `example/e2e/screenshots/`, which belongs to the example suite

The directory is gitignored (so nothing is at risk of being committed, per the repo's no-PNGs rule) and the frames were produced by `playwright screenshot` from `example/e2e/node_modules`, not by the example suite. Housing them under the example suite's output tree, with the same `issue107-` prefix as the suite's own runs, invites the same confusion round 01 flagged: a reader browsing `example/e2e/screenshots/` cannot tell which trees came from the example app and which from a scaffold. A sibling of `ephemeral/screenshots/` (also gitignored) named for the scaffold would keep the two kinds of evidence apart.
