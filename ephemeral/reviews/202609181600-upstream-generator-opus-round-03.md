## Findings

### 1. issue — the documented `just dev` does not work in a fresh clone, and the generated README has no step that makes it work

Caller requirement: *fresh clone … the dev application*. Brief: *no manual configuration or
dependency repair … or undisclosed setup steps*.

Reproduction (`clone/minimal-app`, straight from `git clone`):

```
$ just dev
…/dev: line 13: node_modules/.bin/vp: No such file or directory
skgo: reading skgo.manifest.json from the build: open skgo.manifest.json: file does not exist
$ (cd web && pnpm install --frozen-lockfile)      # exit 0
$ just dev
skgo: reading skgo.manifest.json from the build: open skgo.manifest.json: file does not exist
error: recipe `dev` failed with exit code 1
```

Logs: `minimal-clone-dev-before-install.txt`, `minimal-clone-dev-after-install-before-build.txt`.
Only after an undocumented `just build` does `just dev` start.

Cause: `server.go.tmpl:18` calls `skgo.ReadManifest(dist)` before it looks at `--proxy`, so dev
mode depends on the adapter's build output; that output is ignored by `web/.gitignore`
(`/build/*`), and `Justfile.tmpl:8`–`17` runs `go generate` but neither installs nor builds.
Worklog line 20 found this and fixed it for the generating machine only, by running `vp build`
inside `Create` (`newapp.go:196`–`201`). `README.md.tmpl:13`–`14` says "The generator has already
installed frontend dependencies", which is false for everyone except the person who ran it, and
no section mentions cloning. Impact: every collaborator and every CI checkout of a generated
project gets a failing first command whose error names a file they have never heard of. The `dev`
recipe depending on a build (or the README stating `pnpm install` + `just build` for a clone)
closes it; the generator's own proof could not see it because the dev app was only ever run in
the generated tree.

### 2. issue — `--sv-addon file:` qualification leaves a trap that makes ordinary `skgo new` overwrite tracked files in the skgo checkout

Reproduced twice in this review, unintentionally. `sv`'s `downloadPackage` handles a `file:`
add-on by symlinking it into `sv`'s own install directory, and handles a registry add-on by
un-tarring into that same path without removing what is there (`bin.mjs:1102`–`1118`). The
qualification flag this branch ships (`newapp.go:56`–`58`, `cmd/skgo/main.go:53`) was used earlier
with `file:…/internal/sv`, leaving, in the shared pnpm store:

```
~/Library/pnpm/store/v11/links/@/sv/1.0.0-next.7/f565fffa…/node_modules/node_modules/@skgo/sv
  -> /private/tmp/skgo-upstream-generator-implementation/internal/sv
```

Every later registry-path `skgo new` on this machine extracts `@skgo/sv@0.5.0` *through* that
link: `internal/sv/package.json` becomes the published manifest (version `0.5.0`, reformatted, no
trailing newline) and `sv-addon.js`, `README.md`, `LICENSE` are replaced by the published bytes.
Today those three are identical, so only the manifest shows in `git status`. The first time
`sv-addon.source.js` changes and the bundle is rebuilt, a routine `skgo new` will silently revert
the working tree's bundle to the old release, and what gets qualified, committed or published
next is not what the author built. It also means that on this machine a "registry" run and a
`file:` run are the same directory, so neither can be distinguished from the other after the fact.
The mechanism is upstream's, but the hazard is created by this branch's documented qualification
path and nothing warns about it or cleans it up; the link is still there now. Removing the link,
and qualifying from a packed tarball/scratch copy rather than the live checkout, removes the
hazard rather than documenting it.

  `SKGO_DEV_PORT`. Two generated projects cannot show Storybook at once.
