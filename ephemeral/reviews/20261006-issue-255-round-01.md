### 1. Nitpick: the repair's Conventional Commit type decides whether the merge publishes a release

The plan says the session "does not … publish a release". It does not say
that the approved repair merge feeds `release.yml` directly. On a push to
main, a passing qualification is followed by `skgo-release-version`, and a
`fix:` title is a releasable type (`internal/releaseversion/releaseversion.go:53`).
Everything since `v0.18.0` is `test:`, so a `fix:` squash title on this repair
would tag `v0.18.1` and push it (`.github/workflows/release.yml:188-207`) for
a change that touches only a test file. That tag is outward-facing and hard to
reverse.

The issue title starts with "Regression", which nudges an implementer toward
`fix:`. Prior fixture work (#252, #254) used `test:`, so the risk is low. One
clause in the repair boundary would close it: the PR is titled `test: …`.
