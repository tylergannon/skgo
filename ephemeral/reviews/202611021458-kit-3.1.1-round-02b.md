## Finding

### 1. nitpick — the release notes reverse the malformed-reroute trigger

**Evidence:** `SVELTEKIT_COMPATIBILITY.md:58`; `ephemeral/sveltekit-current/SKILL.md:74-75`; installed Kit `src/runtime/server/respond.js:301-307` and the corresponding official 3.1.0 → 3.1.1 source diff.

The journal describes rerouting **to** a malformed pathname, and the skill describes malformed reroute **output**. The newly fixed case is a malformed original request pathname that `reroute` rewrites into a valid pathname. The old code already guarded `decode_pathname(resolved_path)`; it subsequently decoded `url.pathname` outside that guard. Version 3.1.1 moves this second decode into the guard too. This is visible in the [official fix](https://github.com/sveltejs/kit/commit/1d21a3b) linked by the [3.1.1 release](https://github.com/sveltejs/kit/releases/tag/%40sveltejs%2Fkit%403.1.1).

The accompanying Go explanation also points at the renderer's `Match` callback returning no match, rather than clearly identifying the request boundary. `middleware.go:193-212` directly rejects malformed effective reroute paths with 400; downstream handlers validate the original request path as well. `example/reroute_test.go` exercises successful reroutes and a missing-route control, while `routing_path_test.go` exercises malformed original paths without a reroute; neither is a specific regression witness for the newly fixed upstream combination.

**Impact:** the source-audit notes direct a future maintainer to the wrong side of the reroute operation. This is a documentation precision problem, not evidence of a failing application path. Describe the malformed original URL → valid reroute case accurately and cite the relevant Go request boundary. This does not block the dependency adoption.
