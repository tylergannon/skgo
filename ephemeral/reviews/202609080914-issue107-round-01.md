## Assessment of the implementation

The template now matches the example's dispatch order exactly: `loads.Intercept(remotes.Intercept(endpoints.Intercept(pages)))`, endpoint registry handed to `SSROptions.Fetch` in both arms, `ReadDevManifest` + `NewDevSSR` + `NewDevPages(target, manifest, ssr, log.Printf, endpoints)` in dev, `endpointCfg.Dev = true`, and the `endpoints` variable declared before the closure that captures it. The remaining differences from `example/server.go` (the `Handle` hook, `Transport`, `HandleError`, the dev-added live-route load) are all app-specific features the scaffold does not have, and `generated.Transport()` does not exist for an app without hooks, so they cannot be mirrored unconditionally. The scaffold test's endpoint assertions are anchored in fixture strings (`202`, `text/x-skgo-probe`, `X-Skgo-Handler`, a literal body) that the app cannot have produced any other way, and the dev assertions check Go-rendered markup before Vite could answer. That part of the work is sound.

## Findings

### 1. Issue: acceptance "A page can call the route through SSR-time `event.fetch`" is not demonstrated

Issue #107 lists this as an acceptance criterion. The scaffold has no page, `+page.ts`, or `+page.server.ts` that fetches anything (`internal/newapp/template/web/src/routes/` holds only `.svelte` files and `hello.remote.go.tmpl`), and `scaffold_test.go` never triggers a render-time fetch. The only thing the branch does for this criterion is pass `Fetch: endpoints.Intercept(http.NotFoundHandler())` in `server.go.tmpl:66` and `:81`, which the worklog explicitly re-scopes as "composition" rather than behaviour.

Nothing in the tree covers the gap either: the only `Fetch` tests are `internal/ssr/ssr_test.go:225` and `:256`, which drive a stand-in bundle, and the example suite's "A page reads the endpoint" scenario is a browser-side `fetch` in `example/web/src/routes/api/+page.svelte:27`, not `event.fetch` during a render. Mutation check: delete both `Fetch:` lines from the template and `TestAScaffoldedProjectBuildsAndServes` still passes, because no render ever calls fetch. `CLAUDE.md` says to "never claim anything that hasn't been demonstrated running"; the issue's own wording ("A page can call the route") asks for a page that does it. Either the scaffold test needs a page whose Go-rendered document carries a value it got from the probe endpoint through `event.fetch`, or the criterion should be reported as not met, not silently narrowed.

### 2. Issue: the offered proof artifacts do not exercise the change

The diff touches only the scaffold template and its test. `example/` and the library are untouched. The two screenshot trees under `example/e2e/screenshots/issue107-*` are therefore a regression run of the example app over code that did not change, and prove nothing about a scaffolded app in either mode. There is no screenshot of the generated app answering `/api/probe`, of its Go-rendered dev home page, or of anything the issue is about. `CLAUDE.md` requires artifacts "a human can look at without reading code or rerunning anything: screenshots of the running app at the moment each scenario asserts". The scaffold test's assertions are good ones, but they are an exit code. Impact: a reviewer who follows the repository's own rule cannot accept the change from what was handed over.

### 3. Issue: the dev-mode proof contains blank frames where prod shows the page, and was handed over unexamined

Comparing the two trees, 12 frames are blank in prod and 49 in dev. 37 are blank only in dev. Most are "the document already said ..." steps that never navigate in a way the browser paints, which is a pre-existing property of the suite. But `issue107-dev/ssr/The-home-pages-HTML-already-contains-the-site-name/03-And-the-site-is-named-skgo.png` is blank after `Given I open "/"` and a passing `expect(page.getByTestId('site-name')).toHaveText("skgo")` (`example/e2e/steps/colocation.ts:32`), while the prod frame of the same step (`383818` bytes) shows the full home page. A passing DOM assertion beside an all-white frame of the same page is exactly the mismatch `CLAUDE.md` says is "the single most valuable thing an agent can find", and it was not reported. Separately, `issue107-prod/routes/A-page-reads-the-endpoint-and-shows-what-it-returned/04-*.png` shows "calling the endpoint..." rather than the returned todo the step claims, so that frame does not show the asserted state either (the dev frame does). None of this is caused by the diff, but it is the evidence the branch relies on, and `CLAUDE.md` says never to hand over a screenshot you have not looked at.

### 4. Nitpick: a scaffolded app that later adds a `transport` hook has no wiring path documented

`example/server.go` sets `remoteCfg.Transport` and `loadCfg.Transport` after the dev branch (with a comment explaining why placement matters), but the template cannot, because `generated.Transport()` is only emitted when `src/hooks.ts` declares one (`internal/gen/emit.go:634-638`). That is a legitimate reason for the composition to differ, but the generated README (`README.md.tmpl`) says nothing about it, so a user who adds a transport hook gets a generated `Transport()` the server never mounts and a client that cannot decode the response. One sentence in the README pointing at the two config fields would close it.

### 5. Nitpick: the worklog's pinned-source claim is imprecise

`ephemeral/worklog/202609080857-scaffold-endpoint-dev-stack.md` says the root inspiration tree "has no `junkyard` directory". The directory exists at `/Users/tyler/src/skgo/ephemeral/inspiration/junkyard` but is empty, and the `sveltekit-current` skill path is indeed missing. The actionable half (the required SKILL.md is absent) is right; the housekeeping change it asks for should be scoped to restoring the junkyard contents, not creating the directory.
