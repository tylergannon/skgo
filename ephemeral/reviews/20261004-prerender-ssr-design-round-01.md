## Finding 1 — issue: the subset leaves public client-asset authority implicit, including URLs absent from prerender inventory

The proof at worklog line 9 requires the actual SSR document and matching static response to agree, while the store inherited from the preceding plan is introduced as an authority built from `Manifest.Prerendered` and embedded files. The preceding plan's line 284 separately requires preservation of client-asset priority, but the subset references its SSR ordering region (299–318) without making this prerequisite or its proof explicit. A store consulting only the listed prerendered tree cannot establish the requested equality.

Current `static.go:671–678` selects a client asset before the prerendered remote branch at `:681`. Native Kit's `runtime/app/server/remote/prerender.js:97–125` likewise obtains the public URL's successful response before validation/body execution; it does not require that URL to appear in the prerender path inventory. Therefore there are two necessary cases:

- A registered remote URL has both `client:atlas` and a recorded prerendered `build:atlas` result: HTTP and SSR must select `client:atlas`, with Go body calls exactly zero.
- The registered remote URL has a public client result but no prerender membership: native public/static authority still wins. Refusing it as a missing non-dynamic input would make HTTP return a valid result while SSR returns 500.

Unlisted files in the prerendered tree and physical mapped storage remain unauthorized. That restriction must not accidentally remove the existing public client namespace's authority. Conversely, client precedence must not waive validation of a missing/corrupt artifact still required by recorded inventory.

**Bounded correction:** make client-first selection an explicit shared static/SSR artifact-store contract for a known registered prerender URL. Add supplied, distinct client/build/live values and both membership cases to the literal Go HTTP/compiled SSR controls, with runtime body count zero. A deliberate reversal/removal of client authority must fail those controls. No socket fetch, JS I/O, dynamic fallback API or remote interceptor rewrite is needed for this prerequisite.

## Finding 2 — issue: startup corruption validation is not distinguished from app-specific result revival

Worklog lines 9–11 require missing/corrupt recorded remote files to refuse construction and preservation of result transport, but do not specify how the shared authority validates transported payloads at both constructors. `NewStaticHandler` accepts a build filesystem and static options, with no Transport argument (`static.go:330`); `NewSSR` receives the registered remotes and their Transport (`document.go:132`). The existing example also constructs SSR before the static handler (`example/server.go:242–253`). These are distinct construction contexts, and standalone static serving is supported.

The preceding plan correctly says SSR must parse with **result** `Transport.revivers()` rather than `argumentRevivers()` (plan lines 299–302; `transport.go:195–233`). That settles result decoding but not transport-independent startup validation. The installed Go devalue parser requires a supplied reviver for a custom tag and otherwise returns `Unknown type <tag>` (`polytype@v1.3.0/devalue/parse.go:220`, `:354`). Parsing every recorded result with nil revivers in the shared static store would reject a valid transported build. Validating only the outer JSON envelope would allow corrupt devalue slot references or invalid encoded result data through the stated corruption gate.

**Bounded correction:** specify which layer performs structural envelope/devalue validation, which performs actual result revival, and where each construction failure must occur. Keep the raw stored wire bytes and raw cache keys intact; static construction must not invoke argument decoders or require a new parameter/input contract. Require a positive transported artifact through standalone static construction and actual compiled SSR class-method use, plus negative malformed envelope, malformed devalue/reference, missing recorded file and result-revival failure controls at the applicable constructors. The implementer can use the existing Go devalue facilities; a second JS decoder, public API redesign or hand-written remote schema is not justified by this ambiguity.

## Source contracts otherwise sufficiently settled

The existing-declaration subset does not require Inputs, dynamic option emission or parameter-core integration. Existing generated typed and noarg prerender exports already participate in the build bridge (`internal/gen/emit.go:204–212`); native build output can supply the runtime fixture. NewSSR currently executes Go for SSR (`document.go:1421–1488`), so the declared artifact-first seam is concrete.

The native wrapper ordering is load-bearing and sufficiently explicit in the preceding reviewed design. `exports/vite/build/remote.js:72–89` replaces non-dynamic production declarations, including noarg declarations, with `prerender('unchecked', throwingBody)`. `runtime/app/server/remote/prerender.js:85–95` derives the key from the original raw argument before fetching/reusing built data. Only after that attempt does it run validation/body (`:134–139`). The Goja production wrapper therefore must select the native unchecked form before any original noarg validator can reject null. A change only to `SSR.answer` cannot prove the required production 500 versus dev 400 distinction. Current `app-server.js:65–72` retains the original noarg overload, so the actual compiled component control is essential. Existing `esm-env` production/dev definitions (`env.js:211`, `:669`) provide the required environment distinction without a new environment design.

Built error and redirect classification is also explicit and source-correct. Native built errors throw `HandledHttpError` (`prerender.js:119–122`); `runtime/server/errors.js:21–24` returns that body before running `handleError`. A carried already-handled signal must survive the engine result into Go's document error handling, preserving custom fields and avoiding a second hook execution. It must be scoped to that error rather than poisoning later render failures or pooled runtime reuse. Current `entry.js:49` and `handle_error.go:93–111` have no such fast path, identifying the narrow required surfaces.

Native built result parsing returns `parse(data)._` (`prerender.js:124`). A result envelope containing only `redirect` therefore yields true undefined, whereas a live thrown Redirect retains document redirection. The planned literal compiled-component/error/redirect tests must distinguish undefined from null, a missing hydration entry and a document redirect. Successful built values must be filed under the original `p` key with result transport preserved; source-only host callback assertions do not prove hydration behavior.

The planned missing non-dynamic refusal, valid dev execution, inventory refusal, literal live/body counters, noarg null and raw key controls are appropriate future obligations. Browser proof is appropriately limited to hydration with zero remote requests and scripting-disabled navigation showing the supplied built value. Existing private-query, static method/slash/compression and legacy encoded-path limits remain pertinent regression controls. HTTP interception, dynamic fallback, declaration inputs and parameter semantics must not be advertised as solved by this subset.
