# Kit metadata publication prior art

**Verdict.** The closest useful pattern is to let Kit produce the route/module graph and use Kit's manifest object as Go's graph input. Neither Vite's backend asset-manifest integration nor another runtime-provider's HMR bridge solves Kit's structural graph identity or alone prevents Go from serving a mismatched node. These two inspected patterns do not provide a ready-made SKGO publication policy; that is a bounded finding, not an exhaustive claim about all Vite integrations.

## Closest demonstrated patterns

1. **Kit's own dev manifest refresh is the structural source of truth, but its callback fires too late to gate Kit's writes.** The installed, pinned package is Kit `3.0.0` (`example/web/node_modules/@sveltejs/kit/package.json`). Its dev `update_manifest` calls `create_manifest_data`, writes Kit's generated dev files through `sync.create`, invokes `set_manifest_data(manifest_data)`, validates route parameter modules using Kit's Vite SSR runner, then replaces its SSR manifest with `generate_manifest`. Add/unlink events under routes, matchers and remotes are debounced for 100 ms before that path runs. The callback is *after* `sync.create`, so Kit has already written generated client files (including node-indexed imports) before a consumer can inspect `ManifestData`. The Vite plugin callback presently only assigns the object reference; it does not wait for Go to compile/register the matching graph. See [dev/index.js:102-145](../../../example/web/node_modules/@sveltejs/kit/src/exports/vite/dev/index.js) and [dev/index.js:228-238](../../../example/web/node_modules/@sveltejs/kit/src/exports/vite/dev/index.js), [vite/index.js:571-581](../../../example/web/node_modules/@sveltejs/kit/src/exports/vite/index.js), [generate_manifest.js:45-85](../../../example/web/node_modules/@sveltejs/kit/src/exports/vite/dev/generate_manifest.js). Thus the object is the copyable graph input, but this callback is not a publication barrier. A consumer needs a policy that prevents wrong-node responses; during structural update, explicitly waiting/unavailable responses and reload may be sufficient. No arbitrary filesystem transaction is implied.

   Separately, the current adapter's `snapshot()` calls Kit's private scanner and `sync.create` itself ([dev.js:101-116](../../../internal/adapter/skgo-adapter/dev.js)). This duplicates some orchestration and is not the manifest callback. In the overlapping structural edit, Kit's generated client referenced node `50` while Go's still-published renderer graph had not caught up; the browser showed an Internal Error with `wrongNodeFrame` at the old optional route. The actual browser observation is preserved in [route-held-browser.json](../20261015-overlap-answer/route-held-browser.json). This demonstrates the failure to avoid, not a required duration or a particular publication mechanism.

2. **Cloudflare's Vite plugin is a working Vite-managed external-runtime provider, with a narrow lesson.** At pinned Workers SDK commit `68f86a32`, its custom `CloudflareDevEnvironment` extends Vite's `DevEnvironment`, so Vite retains the environment/module graph and HMR ownership while module invocation crosses into Miniflare through a binding. It buffers HMR messages until the Workerd runner's WebSocket is initialized, then flushes them. A Workerd crash restarts Vite because the runner, channel and environment tied to it are gone. See [cloudflare-environment.ts:33-105,108-143](https://github.com/cloudflare/workers-sdk/blob/68f86a32cb9f9fb8a8875bb5b2121c30b70c7b4c/packages/vite-plugin-cloudflare/src/cloudflare-environment.ts#L33-L143), [miniflare-options.ts:587-609,676-687](https://github.com/cloudflare/workers-sdk/blob/68f86a32cb9f9fb8a8875bb5b2121c30b70c7b4c/packages/vite-plugin-cloudflare/src/miniflare-options.ts#L587-L609), and its early-HMR test [hmr-events.spec.ts:17-58](https://github.com/cloudflare/workers-sdk/blob/68f86a32cb9f9fb8a8875bb5b2121c30b70c7b4c/packages/vite-plugin-cloudflare/src/__tests__/hmr-events.spec.ts#L17-L58). This is closer to shared graph ownership than exporting a separate graph snapshot, but its evaluator is Workerd, not goja. The runtime bridge and recovery are substantial and Workerd-specific; it does not coordinate Kit's route/node metadata with a Go server. The reusable idea is to keep Vite's graph and HMR decisions in Vite and make readiness/notification explicit across the runtime boundary. Whether current Vite+ Core's environment boundary could be paired with Go/goja is unproved.

## Boundary for SKGO

Kit's renderer manifest uses its generated node index in both `client/nodes/<index>.js` and `client.routes` records (see installed source `example/web/node_modules/@sveltejs/kit/src/exports/vite/dev/generate_manifest.js`, lines 45-70 and 82-84). Those are Kit identities. SKGO must publish a renderer and the matching Go route/remote tables against that same structural revision before exposing the corresponding client graph. A separate Vite backend asset manifest describes URLs/assets; it does not carry this Kit SSR identity. The full-build `adapt(builder)` boundary is a supported complete publication path, but it is not the live development refresh protocol.

The concrete reuse candidate is therefore Kit's manifest data as the single graph input, with a revision tying renderer build and generated Go registrations to the corresponding client graph. The unresolved SKGO-specific work is the handoff/readiness policy that avoids wrong-node responses when Kit's client graph changes before Go is ready, plus behavior on a failed Go candidate. A temporary wait/unavailable response and reload may be acceptable. Neither inspected precedent supplies that exact SKGO policy.
