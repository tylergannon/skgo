# Instance listener discovery evidence (2026-10-15)

Research only; no topology selected. Installed `@sveltejs/kit` is 3.0.0. This worktree's `example/web/vite.config.ts` sets `kit.paths.origin` from `ORIGIN` (default `http://127.0.0.1:8080`), matching Kit 3's build-time fixed-origin constraint documented by `ephemeral/sveltekit-current/SKILL.md`. Source `example/web/node_modules/@sveltejs/kit/src/exports/vite/index.js:497` embeds `kit.paths.origin` as `__SVELTEKIT_PATHS_ORIGIN__`; core validation is in `src/core/config/options.js:194-213`. Thus an ephemeral actual listener address can be discovered at runtime, but a varying port cannot be assumed to rewrite Kit's built origin automatically.

Pinned Vite source is the cache's readable upstream Vite 8.3.1 (not VitePlus artifact identity). In `repos/dev-experience-20261015/frameworks/vite-8.3.1/docs/config/server-options.md:55-73`, `server.port` defaults to 5173 and Vite tries subsequent available ports unless `strictPort`; `strictPort: true` exits on conflict. Source `packages/vite/src/node/server/index.ts:974-978` updates normalized `server.config.port` from `httpServer.address().port` on `listening`, proving Vite internally knows its actual port after fallback. The public server object exposes `httpServer`; the upstream `createServer` API docs and type should be checked for the integration surface if needed.

HMR has an independent address dimension. Pinned docs `server-options.md:224-246` say reverse proxies are expected to proxy WebSocket; failed HMR websocket attempts fall back to a direct connection to the Vite HMR server. Documented ways to avoid fallback are proxy websocket, strict fixed port plus matching `server.ws.clientPort`, or separate `server.ws.port`. Therefore a proxy's HTTP target may be retargetable while the browser HMR client still points elsewhere; emitted client config/address must match the reachable socket. A dynamically shifted Vite port needs explicit observation/configuration or proxying that avoids direct-address assumptions. Exact behavior with port 0 plus configured `ws.clientPort` was not established here.

Vite `server.origin` (`server-options.md:453-463`) controls development asset URL origin and is distinct from its actual listen port. Upstream `server.origin` is a configured URL, not an address-discovery callback.

Go's standard `net.Listener` reports the bound address through `Listener.Addr()` after `net.Listen`; binding port 0 asks the OS for an available ephemeral port. The exact public endpoint can therefore be derived from the owned listener itself rather than a check-then-bind port probe, and remains attached to that listener across application child restart. This standard-library fact was not copied into the cache as a code experiment; no process/listener experiment was run per mission.

Prior art: cached older SKGO `repos/skgo-current/internal/dev/server.go:38-60` explicitly makes the Go session own the public listener, proxies Vite websocket traffic to a configured Vite URL, and forwards application traffic to a private child. `potential-experiments/supervisor-listener-owner.md:5-9` records that as historical prior implementation, and notes alternative Vite front door. It is not evidence for current checkout behavior. Wails prior art documented in `index/dev-go-prior-art.md` discovers/selects the Vite URL before watcher startup, but that is config coordination, not proof for concurrent port-zero instances.

Concurrent-instance implication (inference): fixed default ports and check-then-bind selection are race-prone when several `skgo dev` sessions start together. Kernel-assigned port-zero binds avoid that allocation race, but every consumer (browser origin, Go↔Vite proxy, spawned app, HMR client) must receive the actual address from the owner. On Go app restart, a stable supervisor-owned listener avoids changing the browser-facing endpoint; if the app owns its listener, restart changes/disrupts that endpoint and requires readiness/discovery coordination. Whether a separate Go listener is required remains architecture-dependent.

Uncertainties: no current integration fixture tested simultaneous instances, browser-facing Kit URL generation under port zero, Vite HMR fallback when its port shifts, or proxy retargeting while Go restarts. Kit's configured build origin appears fixed; how the app's chosen origin can be allocated while satisfying that constraint is unresolved here.

## Kit 3 dev route and remote metadata lifecycle addendum

The installed Kit 3.0.0 Vite dev plugin already detects structural route changes. `src/exports/vite/dev/index.js:225-238` watches add/unlink for files under routes, params and client hooks; it debounces add/unlink by 100 ms and calls internal `update_manifest`. `update_manifest` (`:101-145`) rescans with Kit's `create_manifest_data`, runs `sync.create`, publishes the new data to Kit plugin closures, validates matchers by importing the params module, emits full-reload if a prior manifest error is repaired, then replaces its internal generated SSR manifest. Page/layout/server changes use `sync.update` where possible and otherwise schedule a full manifest refresh. Requests await initial manifest setup and then call Kit's own `respond` with this live manifest (`:311-316`, `:430-449`). This is Kit's supported internal dev lifecycle; there is no documented/public callback exposing the refreshed SSR manifest to an external Go process.

`src/exports/vite/dev/generate_manifest.js:25-33,82-175,177-209` describes what the internal object contains: indexed node loaders for component/universal/server modules, lazy inline CSS dependency traversal, remote loaders derived from current `get_remotes()`, route records with id/pattern/params/page branch/endpoint loader, and a lazy `matchers()` import of the actual params module. This is richer than route names or static filenames. `src/exports/vite/plugins/remote.js:101-135,158-183` shows remote metadata originates from transformed server remote modules (file hash + file path, then export `__.type` introspection in dev); these transformations support Kit's browser client and Kit's own server manifest. Vite hot events exist for clients (`index.js` full-reload path), but the source inspected has no event payload that serializes all refreshed route/node/matcher/remote metadata to a non-Kit Go consumer. `sync.create` writes Kit generated source/type artifacts, not an evident Go manifest (`core/sync/write_server.js:68-114` only writes server.js/error template). Thus a Go integration must observe/capture/infer Kit outputs through a concrete seam; upstream itself does not supply a Go metadata feed.

Previous cooperation fixture used a fixed handwritten `skgo.Manifest` with exactly three indexed nodes (layout, error, leaf), one `/` route, one server load module, and one SSR client bootstrap path; it separately registered one Go remote and one Go load (`/Users/tyler/src/skgo-token-cache/experiments/architecture-20261015/cooperation/source/cooperation_test.go:110-145`). The frontend control only edited component text, rebuilt the artifact renderer and reinstalled it; route set and node table did not change (`:186-204`). Its README explicitly excludes live add/delete routes and metadata refresh (`experiments/architecture-20261015/cooperation/README.md`, Source mapping and limits). The experiment therefore proves fixed route metadata cooperation, not Kit's structural update reaching Go.

Small structural discriminator: start with the actual cooperation fixture and add one endpoint route (`src/routes/probe/+server.ts`) while Vite remains running; capture the result of Kit's native watcher/manifest refresh and ask the Go responder for that exact URL. Then unlink it and repeat. A Go 404/Go route update should track each transition, and a separately observed Kit client full reload can establish notification timing. Keep a unique route id and literal response. This isolates whether fresh Kit structural metadata reaches the Go route table, without conflating Svelte component HMR or renderer graph rebuild. Remote add/remove is a second, distinct probe because client transform metadata depends on export introspection and Go handlers need synchronized IDs/types; don't infer it from endpoint routing.
