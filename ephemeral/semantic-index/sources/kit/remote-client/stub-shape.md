# Recommended shape of a Go-generated `*.remote.ts` stub so kit's transform, types and CSR work

Source basis: the transform and server-side init in
`reference/kit/packages/kit/src/exports/vite/index.js` and
`reference/kit/packages/kit/src/exports/internal/server/remote-functions.js`; factory
signatures in `reference/kit/packages/kit/src/runtime/app/server/remote/*.js`; public types in
`reference/kit/packages/kit/src/runtime/app/server/public.d.ts`. Recommendations are marked
as such; everything else is source-derived.

## Purpose

A concrete, minimal contract for the file skgo's generator emits per Go remote-function
package: what it must import/export so (1) kit's Vite plugin can evaluate it in Node and emit
the correct client proxies with the correct `'<hash>/<name>'` ids, (2) app code gets the same
`RemoteQueryFunction`/`RemoteCommand`/`RemoteForm`/... types it would with a JS implementation,
and (3) the function bodies never run in production (they throw), with the SSR-only paths
called out.

## Key facts (constraints the stub must satisfy)

- The file name must match `/[/.]remote\.[^/]+$/` and live under the Vite root; its posix path
  relative to that root is hashed (djb2, reverse iteration, base36) to form the URL segment
  (`exports/vite/index.js:L650-L654`; `utils/hash.js:L5-L23`). Go computes the same hash from
  the same path (see `client-transform.md`).
- Kit evaluates the module in Node (dev: SSR runner per client transform; prod: `analyse` after
  the server build; also the prerenderer for `prerender` exports) and requires:
  - no `default` export (`exports/internal/server/remote-functions.js:L12-L16`);
  - every runtime export has `__.type ∈ {command, form, prerender, query, query_batch, query_live}`
    (`L18-L23`), which is guaranteed by calling the real factories from `$app/server`
    (`runtime/app/server/remote/query.js:L113`, `command.js:L62`, `form.js:L90-L93`,
    `prerender.js:L75-L82`);
  - the top level must not throw.
- The client bundle keeps **nothing** from the file except export names and types
  (`exports/vite/index.js:L703-L757`), so the stub's body content is irrelevant to the browser.
- Import path is exactly `$app/server` (kit 3 kept `$app/*`; docs example
  `reference/kit/documentation/docs/20-core-concepts/60-remote-functions.md:L1089`;
  the client runtime itself annotates types from `'$app/server'`, `runtime/client/remote-functions/command.svelte.js:L1`).
- Required plugin options: `experimental: { remoteFunctions: true }` and
  `compilerOptions: { experimental: { async: true } }` in `sveltekit(...)` (docs `L13-L28`;
  guard at `exports/vite/index.js:L768-L785`).
- Factory overloads that give the desired public types without a schema
  (all take `'unchecked'` as the first argument):
  - `query('unchecked', (arg: In) => MaybePromise<Out>)` → `RemoteQueryFunction<In, Out>`;
    `query(() => ...)` → `RemoteQueryFunction<void, Out>` (`query.js:L18-L64`).
  - `query.batch('unchecked', (args: In[]) => MaybePromise<(arg: In, idx: number) => Out>)` →
    `RemoteQueryFunction<In, Out>` (`query.js:L216-L262`).
  - `query.live('unchecked', (arg: In) => AsyncIterable<Out> | Iterable<Out> | ...)` →
    `RemoteLiveQueryFunction<In, Out>` (`query.js:L120-L160`; return type union at
    `types/internal.d.ts:L361-L369`).
  - `command('unchecked', (arg: In) => MaybePromise<Out>)` → `RemoteCommand<In, Out>`.
  - `form('unchecked', (data: In, issue) => MaybePromise<Out>)` → `RemoteForm<In, Out>` where
    `In extends RemoteFormInput` (string | number | boolean | File | nested, arrays thereof)
    (`form.js` overloads; `public.d.ts:L216-L218`, `L276-L331`).
  - `prerender('unchecked', (arg: In) => MaybePromise<Out>, { inputs?, dynamic? })` →
    `RemotePrerenderFunction<In, Out>` (`prerender.js:L24-L82`).
- With no schema, kit's server-side validator rejects any argument (400) for zero-arg
  functions and passes `'unchecked'` args through (`runtime/app/server/remote/shared.js:L12-L25`).
  This only matters where kit's server runs (dev/prerender); Go validates in production.
- `requested`, `getRequestEvent`, `read` etc. are server-only imports and are not needed in the stub.

## Recommended stub (minimal example)

File: `src/lib/skgo/todos.remote.ts` (hash `kitHash("src/lib/skgo/todos.remote.ts")`;
generator and Go registry must agree on this relative path).

```ts
// GENERATED BY skgo — DO NOT EDIT.
// Implementations live in Go. These bodies exist only so SvelteKit's build can
// discover export names and kinds; they must never execute.
import { query, command, form, prerender } from '$app/server';
import type {
	RemoteQueryFunction,
	RemoteLiveQueryFunction,
	RemoteCommand,
	RemoteForm,
	RemotePrerenderFunction
} from '$app/server';
import type { Todo, TodoFilter, NewTodo, UpdateTodoInput, UpdateTodoResult, Stats } from './todos.types';

function skgo(name: string): never {
	throw new Error(`skgo: ${name} is implemented in Go and must not run in JavaScript`);
}

export const getTodos: RemoteQueryFunction<TodoFilter, Todo[]> =
	query('unchecked', (_arg: TodoFilter): Promise<Todo[]> => skgo('getTodos'));

export const getTodo: RemoteQueryFunction<number, Todo> =
	query.batch('unchecked', (_ids: number[]): Promise<(id: number, i: number) => Todo> => skgo('getTodo'));

export const stats: RemoteLiveQueryFunction<void, Stats> =
	query.live((): AsyncIterable<Stats> => skgo('stats'));

export const addTodo: RemoteCommand<NewTodo, Todo> =
	command('unchecked', (_arg: NewTodo): Promise<Todo> => skgo('addTodo'));

export const updateTodo: RemoteForm<UpdateTodoInput, UpdateTodoResult> =
	form('unchecked', (_data: UpdateTodoInput): Promise<UpdateTodoResult> => skgo('updateTodo'));

export const siteConfig: RemotePrerenderFunction<void, Record<string, string>> =
	prerender((): Promise<Record<string, string>> => skgo('siteConfig'), { dynamic: true });
```

Notes on the example:
- Explicit type annotations are recommended (not required) so the emitted `.d.ts`-equivalent
  surface is stable even if kit's overload inference changes; the `'unchecked'` overload already
  infers `In`/`Out` from the callback.
- Type imports from a sibling generated `todos.types.ts` are erased at build time; only runtime
  exports are checked by `init_remote_functions`.
- `form` inputs: booleans must be optional in the Go-facing type because unchecked checkboxes
  send nothing; numbers/booleans arrive typed only when inputs are created with
  `fields.x.as('number'|'checkbox')` (`n:`/`b:` prefixes, `runtime/form-utils.js:L26-L63`).
- Every exported name becomes a URL: `/_app/remote/<hash>/getTodos` etc. Keep names stable.

## SSR-only / build-time paths (what the throwing body would hit)

- **Prerender at build.** Kit's prerenderer executes every `prerender` export (all `inputs`)
  during `vite build` (`core/postbuild/prerender.js:L659-L719`); with a throwing body the
  response is `type:'error'` with a non-200 status while prerendering
  (`runtime/server/remote-functions.js:L345`) and `handleHttpError` (default `fail`) aborts
  the build (`core/postbuild/prerender.js:L186-L199`). Two workable designs (recommendation):
  1. *Go serves during build:* the stub's prerender body does
     `fetch(process.env.SKGO_BUILD_ORIGIN + url).then(r => r.json())` and returns `parse(data)._`;
     kit saves the result to `output/prerendered/data/_app/remote/<hash>/<name>[/<payload>]`
     (`prerender.js:L432-L433`, `L457-L470`, `L544`) and Go serves those files statically.
     `inputs` can likewise be fetched from Go.
  2. *Dynamic only:* set `prerender: { handleHttpError: 'warn' }` (or list no prerender inputs),
     mark stubs `dynamic: true`, and have Go answer prerender URLs at runtime; the client's Cache
     API caches them per app version anyway (`runtime/client/remote-functions/prerender.svelte.js:L11-L32`, `L86-L112`).
  Design 2 is simpler and needs nothing from Node at build; design 1 yields true static output.
- **Dev server.** In `vite dev`, kit's own server answers `${base}/${app_dir}/remote/*` and would
  run the stub (500 with the `skgo:` message). Put Go in front of Vite for that prefix, or add
  `server.proxy` for `^/_app/remote/` → Go, so the browser only ever talks to Go.
- **Hydration seeding.** `payload.data.{q,l,f,p}` from an SSR'd page pre-populates
  `query_responses`/`prerender_responses` (`runtime/client/client.js:L500-L510`). With no SSR
  these are empty and every query fetches on first use — no stub involvement.
- **Non-enhanced form POST.** A `<form>` without the attachment (or with JS off) posts
  `multipart/form-data` to the page URL with `?/remote=<id>`; kit handles it inside page
  rendering (`runtime/server/page/index.js:L62-L64`) and re-renders with `f` data. Without
  SSR, Go should either reject (405) or run the form and `303` back; issues cannot be shown.
- **`isRemoteRequest`/`refresh()` in native submissions.** Irrelevant without SSR.
- **Server-side calls between remote functions** (a query awaited inside a command) are a JS
  server concept; in skgo the Go handler composes Go functions directly and adds `q` nodes.

## Go implementation notes

- Generator inputs per function: Go package path → stub file path (relative to Vite root),
  export name, kind, TS input/output types. Emit the stub and a sibling `*.types.ts`; register
  `{hash, name, kind}` in the Go router so URLs match. Add a Go test that recomputes the hash for
  each emitted path and compares with a golden produced by kit's `hash.js` (`worolc` for
  `src/lib/todos.remote.ts`).
- Kinds map 1:1 to Go handler behaviour documented in `client-requests.md` /
  `client-expectations.md` / `live-and-batch.md`: `query` GET + `q`; `query.batch` POST `payloads`;
  `query.live` GET SSE; `command` POST JSON + `refreshes`; `form` POST binary form; `prerender`
  GET with path payload.
- Expose in Go: a `requested(fn, limit)` equivalent for commands/forms, `refresh`/`set` that add
  `q` nodes and flip `r`, `reconnect` that adds `l` nodes.
- Guard the build: fail fast if a stub path contains characters outside ASCII (hash correctness
  with non-BMP chars is untested), or if two Go functions map to the same `(hash, name)`.

## Gotchas

- Changing the stub's path changes the hash and therefore every URL and every client cache key;
  treat the path as part of the public contract.
- Do not add non-remote runtime exports (constants, helpers) to the stub: kit's init throws.
  Type exports are fine.
- Don't `export default`.
- A stub body that is an `async function*` (live) would not throw until iterated; using a plain
  function that throws is fine because kit only reads `__` at build, but the `dev`/prerender paths
  above are where it would be called.
- `query.batch` with `'unchecked'` needs the callback to return a *getter* type
  `(arg, idx) => Out`; annotate `Promise<(id: In, i: number) => Out>` or TS will infer `Out` wrong.
- If the app defines a `transport` hook, its encoders apply to the client's argument encoding and
  its decoders to responses; Go must implement the same named codecs or reject those types.

## Recipes

- Vite config the generated app needs:
  ```js
  sveltekit({
  	adapter: skgoAdapter(),
  	compilerOptions: { experimental: { async: true } },
  	experimental: { remoteFunctions: true },
  	prerender: { handleHttpError: 'warn' } // only if using design 2 for prerender stubs
  })
  ```
- Dev proxy (design: Go in front): run Go on `:3000`, Vite on `:5173`, Go reverse-proxies
  everything except `/_app/remote/` to Vite; or in Vite `server.proxy: { '/_app/remote': 'http://localhost:3000' }`.
- Smoke test after generation: `vite build` must pass; grep `.svelte-kit/output/client` for
  `__remote.query('<hash>/getTodos')`-style calls (minified names vary; search for the id string).
