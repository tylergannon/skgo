## Q4 — Does the public API allow attaching a doc comment to a declared function or type?

**Supported: no, not through `Declare`/`Declaration`. Documentation comes only
from Go source comments (or a `description` struct tag on struct fields), or a
literal string passed to `jsonschema` builders.**

| Bookmark | What it shows |
|---|---|
| `v1.1.0-public-api-no-doc-attachment.md` § A | Exhaustive `*Declaration[T]` method list — no doc-attachment method. |
| same § B | Every package-level `func` in the root package; exported configuration helpers are `Field`, `Compose`, `ResolveConfiguration`, `Declare`, `SealedUnion` plus legacy `NewJSONSchema*`/`With*`/`AsRef`. None takes doc text. |
| same § C — V110 `jsonschema/json_schema.go` L266, L282, L312, L323, L330, L337 | `ConstSchema/EnumSchema/ArraySchema/StringSchema/BoolSchema/IntSchema` take a `description string` — a *literal*, caller-authored, not read from a doc comment. |
| same § D — V110 `internal/utils/rewriter/main.go` L1-L13 | A `go run main.go <file.go> <typeName> <newComment>` utility that *writes* a `TypeSpec` doc comment. It is under `internal/`, so it is not importable by skgo. |

Inference (clearly not source): for JavaScript-form skgo output the doc text
would have to come from skgo's own scan of the Go declaration comments — the
same `Comments()`-style capture polytype uses — because polytype's public API
offers no hook to supply it.

## Supported facts vs. inference

**Supported by local text:** every row in the tables above.

**Inference (mine, not in any source):**
1. Because `Declaration`/`DeclarationSpec` carry no comment field, a
   JSDoc-capable JavaScript emitter cannot obtain docs from polytype's
   declaration API; it must capture Go doc comments itself (or reuse
   polytype's `Comments()` capture, which is `internal/` and not importable).
2. polytype's `writeDoc`/`sanitizeComment` pair is a working, tested JSDoc
   formatter already present in the pinned dependency — but it lives in the
   `typescript` backend, whose output is `types.ts`, not skgo's generated
   stubs.
3. `StructField` docs can be overridden by a `` `description:"…"` `` tag; that
   is a wire-format-level override, not a JSDoc mechanism.

**Contradictions / corrections:**
- Reference tree = rc.9, dependency = v1.1.0 (Q5). `declare.go` differs
  materially between them; `doc_generate.go` does not.
- The topic title says "JSDoc projection requirement", but in polytype the
  word "JSDoc" appears exactly once in v1.1.0 and only in an IDE inspection
  profile (`.idea/inspectionProfiles/Project_Default.xml:248`); polytype never
  uses the term for its own output. Its emission is `/** */` blocks produced
  by `writeDoc`.

**Unresolved / out of scope for this topic:**
1. Whether skgo's generator consumes `typegrammar.Definition.Description` (or
   any polytype output) when emitting its own files — belongs to topic-002's
   generated-file inventory; not checked here.
2. Whether generated **Go** accessor functions receive synthesized doc
   comments (the `internal/builder/printer.go:28` comment-preservation switch
   was noted but the Go emitter was not traced).
3. Provenance of the checked-in `ephemeral/typescript-generation/proof/run-*`
   artifacts (run id and date unknown); used only as an illustrative render,
   not as a spec.
4. Whether `devalue`/other backends project `Description` (not examined).
