# Sprint 004: landing server loads on main

trap (cost the most): main squashed PR #9, so `git merge origin/main` from a
branch that carries #9's *unsquashed* commits has no code ancestor. Git's merge
base was the commit before either lineage started, 39 files came back as
add/add, and the files it did merge cleanly it merged against the wrong base —
`static.go` came out with `dataSuffix`/`htmlDataSuffix` declared twice, which
`go vet` caught, and nothing would have caught a subtler one. The fix is to
name the real base: the branch's last pre-loads tree (`599bd58`), where
`diff base origin/main` is exactly #9's post-fork review fixes and
`diff base HEAD` is exactly the loads work. `git merge --abort`, write
`origin/main`'s sha into `.git/worktrees/<wt>/MERGE_HEAD` by hand, then
`git read-tree -m <base> HEAD origin/main` and
`git merge-index -o git-merge-one-file -a`; `git commit` then makes a real
two-parent merge. 39 conflicts became 6. Do this whenever a branch's work was
also merged upstream as a squash.

trap: a panicking server load did not reset a connection, it killed the
process. Loads run one goroutine per node of the branch (`serveBranch`), and an
unrecovered panic on a goroutine is not recoverable by the handler above it —
`go test` reported the whole package as a panic, not a failed test. The remote
paths already had `Remotes.recovered`; loads and the `handle` hook now have the
same guard. A test that asserts "it answered" is the right shape here, because
the failure mode is that there is nothing left to answer with.

trap: `example/server_test.go`'s `newProdHandler` was a hand-written copy of
`cmd/main.go`'s composition, and it had drifted — it built
`remotes.Intercept(static)` with no loads registry, so it was still asserting
the pre-loads claim that every `__data.json` is refused 404. That is what the
static handler does alone and the opposite of what the app does; the suite was
green over it. A test that reassembles the production stack will drift from it.
The stack moved to `package example`, and the binary and the test now call the
same `NewHandler`.

trap: `getByRole('navigation')` in a shared step became a strict-mode violation
the moment a section layout got a nav of its own — two elements matched, and
the step failed on a page that had rendered perfectly. A shared "the app is on
screen" assertion has to target the root layout by test id; roles are not
unique across nested layouts.

trap: the loads `shot` fixture wrote both modes to one path, so the tracked
evidence under `ephemeral/screenshots/loads/` only ever showed whichever of
`prod` and `dev` ran last, while the claim being made is about both. It is now
split by mode, as the AfterStep frames already were. Related: a *failed* run
leaves a `-final` frame under a name no passing run overwrites, so a failure's
picture can sit in the tracked evidence directory indefinitely — check for
orphans after a red run.

correction: `vp dev --port N` binds `localhost`, not `127.0.0.1`. The Go server
started with `-proxy http://127.0.0.1:N` answers 502 "connection refused" while
`curl http://localhost:N` is fine. Proxy to `localhost`.

correction: main's `internal/gen/ownership_test.go` builds a stand-in `skgo`
package at skgo's own import path, and the generator now emits `SkgoLoads()
[]*skgo.ServerLoad` for every package it writes. The stand-in needs
`ServerLoad` and `NewLoad` or three ownership tests fail with `undefined:
skgo.ServerLoad` in generated code — a failure that reads like a generator bug
and is a fixture gap.

note: the acceptance gate takes `SKGO_PORT` and `SKGO_VITE_PORT`, and now also
refuses to start when something already listens on the app port. Two runs on
8080/5173 have contaminated each other once already; the ports are part of the
worktree's single-writer resource.
