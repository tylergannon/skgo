# SSR in the Go process — slices 1 and 2

Branch `claude/ssr-no-node-sidecar-9e3be4`. What follows changes decisions; it
is not a summary of the diff.

## Kit's own build output cannot be bundled, and this is why

The obvious move — bundle `.svelte-kit/output/server/entries/**` instead of
recompiling the app's `.svelte` files — does not work, and the reason is worth
writing down because it looks like it should.

Kit's server build has already baked the generated stub into each remote
function: `chunks/site.remote.js` holds `query(() => unimplemented())`, and the
user function is captured in a closure that `fn.__` does not expose. There is no
runtime hook to swap it. Redirecting the import instead fails on the other side:
rolldown mangles the chunk's exports (`export { site_remote_exports as n,
getSite as t }`), so nothing can be re-exported by name.

So the substitution has to happen at the module specifier: `$app/server` is
aliased to a shim that keeps kit's real `query`/`command`/`form` wrappers and
replaces only the body. That forces bundling from source, which forces
recompiling `.svelte` with the app's own Svelte compiler in `generate: 'server'`
mode — which is what the adapter now does.

Changing what `skgo generate` emits — a stub that calls Go instead of throwing —
would let kit's own output be used verbatim. It would also destroy the one proof
the project has that Go answered.

## A remote answer must not round-trip through the engine

The spike collected `state.remote.implicit` inside the bundle and handed the
settled values back to Go for `__sveltekit.data`. Go already has those values:
it answered every call. The engine reports `{head, body}` and nothing else, and
Go builds the payload from the calls it answered, keyed `<kind>/<id>/<payload>`
from its own registry. That also makes kit's "omit an entry with neither `v` nor
`e`" rule automatic — an unanswered call is simply not in the map.

## Server-rendering the session means the app can no longer prerender

`<SignIn />` in the root layout awaits a remote query. Move it out of its
pending boundary — which slice 1 requires, or every page refetches the session
on hydration — and `/about` stops prerendering, because a prerendered page's
branch includes the root layout and kit refuses `query()` while prerendering.

Kit's own answer is `building` from `$app/env`: the layout renders the session
only when there is a visitor. `/about` still prerenders, shows no session in the
file the build wrote, and picks one up when it hydrates. Without that guard the
build fails with "Cannot call query while prerendering", which reads like a
skgo bug and is not one.

Anything that adds per-request data to a root layout hits this. It is kit's
rule, not a gap here.

## The engine needs four web globals, not three

The spike found `TextEncoder`/`TextDecoder`, `btoa`/`atob` and `URL`. Two more
turned up the moment a page with a form was rendered, and both are reached from
kit's own code rather than the app's:

- `URLSearchParams` must be **mutable**. `form.action`'s getter does
  `new URLSearchParams(url.search)` and then `.delete('/remote')`. A read-only
  parser gets "Object has no member 'delete'" from inside a component.
- `File` (and therefore `Blob`) must merely **exist**. Kit's form-field proxy
  asks `value instanceof File` before it describes a file input. Nothing ever
  holds one — an upload's bytes are Go's — but the identifier has to resolve.

Both failures surface as a render that throws, so the page silently falls back
to the shell rather than breaking. `TestEveryRouteInTheManifestIsServed` is what
caught them; a suite that only visits the pages it has scenarios for would not
have.

## Deferred load values are awaited, so nothing streams yet

`skgo.Async` still works, but its value is settled before the render starts, so
a component sees the value rather than a promise and `{#await}` renders its
`:then` branch immediately. Kit streams these as `${global}.resolve(id, ...)`
chunks after the document; that is slice 5 work and nothing here does it.

The visible consequence: `/account/orders` no longer shows `orders-pending`, and
the loads scenario that asserted "the fast content is on screen before the slow
content arrives" now asserts that both arrive in the same document.

## A page whose load fails still gets the shell

The renderer declines a branch with an error node, and the client renders
`+error.svelte` off `__data.json` exactly as it did before SSR existed. That is
the error branch (slice 3), deliberately not built here.
`TestEveryRouteInTheManifestIsServed` allows the shell **only** for a route
whose `__data.json` really is an error, so a page that quietly stops rendering
is still a failure.

## esbuild's install script has to be turned off, not ignored

pnpm 11 refuses to run an unapproved install script and exits non-zero, which
kills `mise run build` in a fresh scaffold with a message about
`pnpm approve-builds`. `allowBuilds: { esbuild: false }` in
`pnpm-workspace.yaml` is the fix: esbuild's platform binary arrives as an
optional dependency and its install script has nothing left to do.

## The adapter is one file and svelte-check reads it

`skgo-adapter.js` is type-checked by `pnpm check` through the app's tsconfig, so
its JSDoc has to be right or `go test ./example/...` fails with TypeScript
errors in a file nobody thinks of as TypeScript. The glue the SSR bundle needs
(the entry, the `$app/server` shim, the polyfills) lives in that same file as
`String.raw` template constants, because the adapter is mirrored byte-for-byte
into the scaffold template and one file is one thing to keep in sync.

Two traps in those constants, both of which produce a parse error a hundred
lines from the edit: a backtick anywhere inside them (including in a comment)
ends the template, and a `${` inside them interpolates.
