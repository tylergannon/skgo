# Sprint 003 execution — actionable intelligence

decision: the sprint started with a compile-time enforcement of kit's cookie
rule — `skgo.Query(func(*Event, In))` vs `skgo.Command(func(*CommandEvent, In))`
— so "cannot set cookies in a query" was unrepresentable rather than reported.
Main then landed Tyler's `EventFrom(ctx)` decision ("signature unchanged"), so
that design was reverted: one `*Event` reached through the context, and the
refusal comes back as an error. Kept from the first design: a query refreshed by
a command shares the command's cookie jar but gets its own immutable event, which
is exactly `derive_remote_function_event(event, state, false)` in kit's
`runtime/app/server/remote/shared.js`. `EventFrom` returns a plain `*Event` and
every method is nil-safe, so a helper shared with non-remote code does not branch.

discovery (real bug, not a design point): `*devalue.Object` had no `MarshalJSON`,
so `decodeArg`'s `json.Marshal(tree)` produced `{"NullProto":false}` and **every
struct argument decoded to its zero value**. Nothing caught it in Sprint 002
because the only arguments were strings. Fixed in `internal/devalue`; goldens in
`parse_test.go` pin object order, `undefined` omission, holes-as-null, and the
refusal to marshal NaN/±Inf (devalue's -3/-4/-5). Any future codec work should
assume the parsed tree must survive an `encoding/json` round trip.

trap: a hand-written devalue payload for testing is `[root, ...pool]`, not
`[rootIndex, ...pool]` — index 0 *is* the root. `["t2"]` is the string "t2";
an object argument is `[{"id":1,"text":2},"t1","hello"]`. Getting this wrong
produces a 400 that looks like a server bug.

discovery: polytype rc.9 is a good fit for this, run as `go tool polytype
--typescript <dir> --target <pkgdir>` with cwd at the host module root. skgo
writes the `//go:build jsonschema` marker file itself
(`skgo_polytype_gen.go`: `Schema()` stubs + `polytype.Declare`), so the app
author never writes registration code. Without `--validate` the only new
dependency is polytype itself. `--target` outside cwd works. Maps are rejected
at generation time with a clear message, which is the admission rule enforced by
the generator that owns it.

decision: types.ts placement — a package that already lives under the vite root
gets `types.ts` beside its Go source; anything else (the brief's
`businesslogic`) gets `src/lib/skgo/<pkgname>/types.ts`. Two wire-owning packages
with the same name is an error. polytype overwrites `types.ts` per run, so
one directory per package is not optional.

decision: skgo refuses `*T` and `map[K]V` in a remote In/Out rather than
emitting a declaration that `encoding/json` will contradict — polytype widens
`*T` to non-nullable `T` while Go marshals nil as `null`. The refusal names the
reason and the wrapper to use. Consistent with the "narrowed admitted type set
is the design" decision on the plan worklog.

limitation (must be solved by Sprint 004): **a `.remote.go` cannot live in a
bracketed or parenthesised route directory.** `go list ./...` from `example/`
fails outright — "malformed import path ... invalid char '['" — for any Go file
under `src/routes/todos/[id]/`. The junkyard's link tree does work (verified:
a directory symlink under `example/generated/links/` is importable and builds),
but it does not fix `./...`; that needs `src/routes/go.mod` to make the bracketed
dirs a nested module, and *that* collides with the repo's `go.work`: a `go tool`
invocation with cwd inside a non-workspace module fails, which would break the
polytype step. Sprint 004 needs `page.server.go` in `[id]`, so it has to settle
this — probably by dropping `go.work` or adding the routes module to it. The
generator today reports the situation instead of emitting something that will
not build (`importPath`, `internal/gen/scan.go`).

decision: drift is caught at three points, and each was demonstrated failing.
`skgo generate` writes `web/skgo.remotes.json`; the adapter cross-checks those
hashes against the `remotes:` map in `builder.generateManifest()` and fails
`vp build` if they differ; the list is copied into `build/skgo.manifest.json`,
and `skgo.NewRemotes` refuses to build a registry that does not answer exactly
that set. `Builder` exposes no remote list directly — regexing the generated
manifest source is the only way an adapter can see what kit actually compiled.
The Go check is skipped in dev, where the client comes from vite and the
manifest describes the last production build.

discovery: `vp check`'s type check is oxlint-tsgolint (TypeScript 7), which
AGENTS.md already says cannot build kit 3, and it does not read `.svelte` at
all. The end-to-end type claim needs `svelte-check` — kit's own tool. Added as a
devDependency plus a `check` script; `example/typedrift_test.go` renames one
json tag, regenerates, and requires svelte-check to fail naming
`TodoList.svelte`. `vp check`'s *format* pass still fails on pre-existing files
(oxfmt wants double quotes and two spaces; the app is tabs and single quotes),
so `--no-fmt` is still the usable form and the generated TS deliberately
matches the app's style, not oxfmt's.

trap: the app's `tsconfig.json` had no `include`/`exclude`, so svelte-check
type-checked the minified bundle in `build/` and reported 1500 errors. Fixed by
listing `include` and excluding `build`. `$app/tsconfig` (at
`node_modules/$app/tsconfig.json`) sets compilerOptions only.

trap: a `query.live` stub must be typed as returning
`AsyncIterable<Output>`, not `Output` — kit's `RemoteLiveQueryUserFunctionReturnType`.
The wrong shape still runs, because the client transform discards the body; it
only shows up under a type check. The same applies to `#lib/foo.remote`:
TypeScript will not resolve a subpath import without an extension, so generated
stubs are imported relatively.

friction: leaving a server from an earlier run bound to :8080 made the suite fail
in a way that looked like a product bug — the second process could not bind and
the stale one was serving a mutated store. The rename scenario now creates the
todo it renames, so the whole suite is repeatable against one long-lived server;
verified by running it twice in a row.

note: `example/.air.toml` excluded `example/web` wholesale, which is now wrong —
the app's remote functions live under `example/web/src`. Narrowed to
`node_modules`, `build` and `.svelte-kit`.

note: kit's `secure` cookie default keys on the literal hostname `localhost`, so
an app at `http://127.0.0.1:8080` gets `Secure` cookies. Chromium accepts them
(loopback is a trustworthy origin) — verified by the sign-in scenarios passing in
both modes — but a future non-loopback plain-HTTP deployment will silently lose
its session cookie, exactly as it would under kit.

## Colocation in bracketed route directories

correction: the "limitation" recorded above is wrong on both counts and cost a
sprint. `./...` from `example/` is *not supposed* to reach a bracketed route
directory — `web/src/routes/go.mod` exists precisely so it never descends
there, and the scanner loads those packages through the link import paths
instead. And `go.work` never enters it: the polytype step runs with cwd at the
host module root (`example/`, a workspace module) and is handed `--target
<module>/generated/links/<enc>`, so no command ever runs with cwd inside the
nested routes module. Verified end to end: `go vet ./... ./example/...` and
`go test ./...` are green with the boundary in place.

discovery (the constraint that shapes the design): **`go:embed` refuses a
symlink** — "cannot embed irregular file", and a directory of file symlinks
gives "contains no embeddable files". polytype's `jsonschema_gen.go` embeds the
`jsonschema/` directory beside it, so for the one package linked file-by-file
(the route tree's own root, whose directory holds the boundary `go.mod`) that
output has to stay inside the link directory. Everywhere else the link *is* a
directory symlink, so polytype writes straight through it into the authored
directory. Do not "tidy" the route root's polytype output back beside its
source: the package stops compiling.

trap: `packages.Load` reports a linked package's files at the *link* path,
unresolved. Every path that comes back — `GoFiles`, `Fset.Position(...)` — is a
link path, and every decision about where generated TypeScript goes, or which
`.remote.ts` a function lands in, needs the authored path instead. `goPackage`
carries both (`dir` authored, `loadDir` link) and so does `namedTypes`.

note: `go list ./...` does not follow directory symlinks, so the route packages
are absent from `go vet ./example/...`. They are still compiled and type-checked
— the generated bindings import every one of them — but vet's analyzers do not
run over them. The route root is the exception: its link is a real directory, so
it does get listed. If per-analyzer coverage of route packages ever matters,
name the links explicitly rather than relying on `./...`.

discovery (real bug, found by the first `[...rest]` route): kit's route patterns
are JavaScript regular expressions and a rest segment comes out as
`(?:/([^]*))?` — the empty negated class, which means "any character" in JS and
is a syntax error in Go. The server refused to start. `kitPattern` in
`static.go` translates just that one construct; kit escapes `[`, `^` and `]` in
literal segments (`escape_for_regexp`), so an unescaped `[^]` is always kit's
rest parameter. Anything else ported from a kit regex source deserves the same
check.

note: the boundary `go.mod` skgo writes declares a module path and nothing else
— no `require`, no `replace`. An editor opening a route `.go` file directly may
therefore report unresolved imports for `github.com/tylergannon/skgo`, because
it resolves the file through the authored path rather than the link. Not
observed to break anything in this sprint; if it bites, the fix is a gopls
workspace that includes the link, not requires in the boundary.

note: kit is entirely unbothered by the new files in `src/routes` — `go.mod`,
`*.go`, `jsonschema/`. `vp build` and `svelte-check` are both clean, and the
`.remote.ts` still sits at the authored path, which is what kit hashes.
