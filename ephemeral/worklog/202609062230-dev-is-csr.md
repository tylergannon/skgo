# The dev leg, and why dev turns SSR off

Branch `claude/ssr-no-node-sidecar-9e3be4`. Traps and decisions only.

## `$app/server` is a seam and a load is not, which decides the whole question

Three seams were weighed against pinned kit source. Two of them cannot be built
without giving something up that the project has already decided it will not
give up, and the reason is worth writing down because the third looks like a
retreat and is not.

**Go renders the dev document too.** Dead on the bundle. The SSR bundle is built
by the adapter from *source* — kit's own `output/server` cannot be bundled, for
the reasons in `202609061930-ssr-in-process.md` — and `adapt(builder)` runs only
in `vite build`. `vp dev` has no `builder`, writes no `output/server/nodes/N.js`
(which is where `nodeTable` and the ssr/csr options come from) and no client
manifest. Even granting a bundle, Go would then have to write kit's *dev*
document: `/@vite/client`, the module-graph URLs, and the per-node inlined
styles `packages/kit/src/exports/vite/dev/index.js` collects with
`find_deps` + `?inline` to avoid FOUC. That is a second `render_response`, in
Go, for the mode nobody ships.

**Kit renders and a dev-only `$app/server` calls Go over HTTP.** This works for
remote functions and only for remote functions. The generated `.remote.ts`
imports `query` from `$app/server`, and kit's own wrapper never calls the user
function — the same inversion the SSR bundle already relies on — so aliasing
that specifier in dev leaves the stub throwing and unreachable. A **server
load** has no wrapper: `+page.server.ts`'s `load` export *is* the function kit
calls (`runtime/server/page/index.js` maps `nodes.data` straight onto
`node.server.load`), and skgo's generated body throws inline. There is no
specifier to alias. Making it not throw is the one change
`202609061930-ssr-in-process.md` names as destroying the project's only proof
that Go answered. So `/account`, `/account/orders`, `/pricing` and both
`/error/*` load fixtures would still 500 in dev. The option covers a third of
the surface.

**Dev is CSR.** `export const ssr = !dev` in the root `+layout.ts`. Kit's own
switch, one line, no skgo code: `render_page` returns the shell without running
a single load when `nodes.ssr() === false`, so nothing reaches a stub, and every
value on every page still comes from Go — `__data.json` for a load,
`/_app/remote/...` for a remote function, the `+server.ts` routes as before.
The dev leg went from 39 failures to 0.

What it costs is real and should be said plainly: a developer running `just dev`
cannot see an SSR-only fault — a component that throws only on the server, a
value that does not survive into the engine — until they build. `just build &&
just serve` is that check and it is one gesture. The two alternatives cost a
second renderer or a second wire protocol, permanently.

## `dev` is true in dev, so `csr = !dev` turns CSR off in dev

Written the wrong way round first and it produces a 218-byte document with no
script and no markup, which reads like a broken build. `/plain` declares
`csr = false` in production and needs `csr = dev` here: a branch with neither
`ssr` nor `csr` has nobody left to render it, and kit answers with an empty
shell that boots nothing. Root layout `ssr = !dev`; page `csr = dev`. Both are
reduced last-wins over the branch by `PageNodes.#get_option`, so the page's
`csr` and the layout's `ssr` do not fight.

## A non-literal page option is invisible to kit's static analyser, and that is fine

`statically_analyse_page_options` (`exports/vite/static_analysis/index.js`)
returns **null** for the whole file the moment an exported page option's
initialiser is not a `Literal`. So `ssr = !dev` makes `node.page_options` null,
and kit's dev server stops taking the `page_options?.ssr === false` shortcut
that would skip *loading* the universal module. That is the behaviour wanted:
the module is loaded and its runtime value read. The value the adapter records
in the manifest is read the same way — it imports the built node module — and in
a build `dev` is false, so production still says `ssr: true`.

## Two suites, not one suite told to squint

The temptation was to make each document-bytes step mean two things by reading
`EXPECTED_MODE`. Seventeen steps would have needed it, and each branch is a
place where a scenario can pass in the wrong mode for the wrong reason. Instead
the scenarios whose claim is genuinely mode-specific are written twice, `@prod`
beside `@dev`, and `defineBddConfig({ tags })` generates only the half that
belongs to the run (`tags: 'not @prod'` in dev). `ssr.feature` is `@prod`
whole — it is a feature about the document Go renders — and `dev.feature`
mirrors it claim for claim.

`outputDir` is per mode (`.features-gen/<mode>`). Without it the dev run's
`playwright test` would happily execute the spec files the prod run generated if
`bddgen` ever failed without failing the pipe.

## The tracked screenshots are evidence, and `rm -rf ephemeral/screenshots/*/prod` destroys it

Several features still write frames under names no current step produces —
`form/prod/01-...png`, `gate/prod/A-query-...-05-Then-...png` — left by earlier
step sets. Clearing the directory before a run deletes 72 tracked files the run
will not put back, and the deletion looks deliberate in the diff. Delete only
the frames whose scenario no longer exists in that mode, and let a rerun
overwrite the rest.

## A frame taken on the first `Then` of a CSR scenario is a picture of nothing

In dev the first outcome step often runs while the shell is still booting, so
`shot()` photographs an empty document. Two of the fifty-six dev frames were
blank on the first run. The claim in those steps is about a response already
read, so the step can wait for `app-nav` before it takes the picture without
weakening anything. `magick <file> -format %k info:` returning 1 is how the
whole set was checked rather than by eye.
