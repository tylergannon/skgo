# server-routes — corrections and traps

## Kit renumbers nodes when a route is prerendered, and skgo was not following

The manifest's `nodes` array is positional, and `route.page.leaf` is an index
into it. Those indices are **not** the numbers the built node modules declare.
`generate_manifest` collects the nodes the surviving routes use and hands each
one a fresh consecutive index (`reindexed`, `used_nodes` in
`core/generate_manifest/index.js`), and it is generated from a route list that
**excludes every route with `prerender: true`** (`core/adapt/builder.js`). So
prerendering one page drops that page's node and shifts every later node down by
one.

The adapter's `readNodes` had been reading `export const index = N` out of each
`output/server/nodes/N.js` — the original numbering. The two agreed only while
every node was used, which was true until this branch prerendered `/about`.

The symptom is not obviously a manifest problem: `/account`'s **layout** loaded
correctly (node 2, below the gap) while its **page** loaded nothing (node 6,
renumbered to 5), so it reads like a bug in `Parent` or in the page's own load.
Three `loads.feature` scenarios went red and the Go tests stayed green, because
nothing in Go can see the misalignment.

The fix is to read the order out of kit's own emitted manifest: it writes the
original index into each node's import path (`__memo(() => import('./nodes/6.js'))`)
in the *new* order. `readNodes` now maps through that, and throws if the number
of node imports it can read differs from `kit._.nodes.length`.

**Nothing catches this but a load actually rendering.** `checkServerLoads`
compares the *set* of `+*.server.ts` paths and passed happily — the paths were
all present, just in the wrong slots.

## The scaffold test was green over source it had never compiled

`internal/newapp` publishes the checkout into a throwaway module proxy under a
fixed version, `v0.0.0-scaffoldtest`. The go command treats the module cache as
immutable and keys both the extracted tree and its package index by
`path@version`, so every run after the first compiled the *first* run's source.
The test had been reporting on a checkout it never built.

It surfaced only because a change to the adapter made the stale copy fail out
loud. A change that only added behaviour would have passed.

`scaffoldVersion` is now unique per run (unix nanos appended), and `publish`
clears every earlier `v0.0.0-scaffoldtest*` out of the module cache so the cache
does not grow a copy of the checkout per run. Purging alone was not enough: the
cached *package index* survived the purge in one run and produced
`could not import reflect (open : no such file or directory)` alongside
`undefined: endpointFn` — a file present on disk that the compiler did not see.

## Kit checks CSRF before it matches a route, and the order is load-bearing

`is_csrf_forbidden` runs at the top of `respond()`, before route matching,
before the trailing-slash redirect and before method resolution. Checking it
after method resolution — which is where it first landed here — answers a
cross-site `DELETE` with a **405 and an `Allow` header**, handing an attacker
the route's method list. A Go test pins the 403, and pins that it carries no
`Allow`.

It applies to endpoints, not only to form actions: any `POST`/`PUT`/`PATCH`/
`DELETE` whose content type is absent or form-shaped, from an origin that is not
the app's. A bare `curl -X DELETE` is therefore a 403, not a 405. Browser
`fetch` sends `Origin`, so same-origin calls are unaffected.

## "Prefer the page" is narrower than it looks

For a route with both a `+page` and a `+server`, kit falls back to the page only
when the endpoint cannot handle a **GET, HEAD or POST** (`respond.js`). A
`DELETE` such a route does not declare stays with the endpoint and gets its 405
there. Falling back for every method turns a 405 into a page render.

## `ssr = false` + `prerender = true` emits the shell, and that is still useful

A prerendered page whose branch has `ssr = false` and no server `load` is
written as the app template with an empty body (`runtime/server/page/index.js`,
the `ssr === false` early return). It is not SSR and does not become SSR.

What makes it worth serving is the other half: **kit deletes a prerendered route
from the manifest's route table**, so a prerendered path that is not served from
the prerendered tree is not served at all — it falls through to the SPA
fallback's 404. Kit's client then renders the route anyway, so the page *looks*
right in a browser while the response is a 404. A scenario that only asserts
"I see the About page" passes over that; the status is what catches it.

A page can only be prerendered if **no node in its branch has a `+*.server.ts`**:
kit runs the branch's server loads while prerendering, and skgo's are generated
stubs that throw.

## Ports and the dev proxy

`vp dev` binds `[::1]:5173` only. `-proxy http://127.0.0.1:5173` gets a 502 from
the reverse proxy on every page while the endpoints — which Go answers before
the proxy — work perfectly, so the app looks half-broken rather than
misconfigured. Use `-proxy http://localhost:5173`.

## Not closed, deliberately

The SPA boot document is served uncompressed. `builder.compress` takes a
directory, and the fallback sits at the build root beside `skgo.manifest.json`;
compressing that directory would compress the manifest too. It is ~1.4 kB and
served from memory.

The Svelte MCP server was not loaded in this session, so
`example/web/src/routes/api/+page.svelte` was written without the autofixer. It
is exercised by `vp build` and by six Gherkin scenarios in both modes.
