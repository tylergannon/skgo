# The error branch, and what it changed under the app

Branch `claude/ssr-no-node-sidecar-9e3be4`. Traps and decisions only.

## `transformError` is global, so any boundary with a `failed` snippet moves the status

Kit installs one `transformError` per render (`page/render.js`) and Svelte calls
it for **every** `<svelte:boundary>` that has a `failed` snippet — the app's own
included, not only the ones kit's `Root` puts around each node. It sets
`page.error` and `page.status` and the document is answered with them.

So a component that catches its own failure and renders a nice message still
changes the whole document's status. That is kit's rule and not a skgo choice,
and it is the reason a page whose session boundary fails comes back 500 with the
page fully rendered inside it. Worth knowing before reading a 500 whose
screenshot looks perfect.

## The `error_components` chain is indexed by the *compacted* branch

`build_error_chain` (kit's `runtime/error-chain.js`) skips empty branch slots
while it walks, so its output lines up with `compact(branch)` — which is what
`render_response` renders and what `error_components?.[i + 1]` indexes. Passing
a chain aligned with the uncompacted branch puts the wrong `+error.svelte` on
every node after a hole.

`nearest_error_pages` is the other half and is indexed the other way: `i` is a
slot in the *uncompacted* branch, and the `idx` it yields is a count of
uncompacted slots to keep. Both are ported literally in `document.go` for that
reason; they look interchangeable and are not.

## `respond_with_error` keeps the route id, and that is load-bearing

Kit hands `respond_with_error` the original event, so `event.route.id` is still
the route that failed. Passing `""` instead — which looks harmless, since the
node being rendered is the root layout and the root error page — makes the retry
render a *different* page than the one that just failed. The fixture that proves
it is `/error/render`, where the root layout throws for exactly one route id:
with the id dropped, the retry succeeds and the visitor gets a 500 error page
instead of kit's `error.html`.

## Kit's `Redirect` constructor needs `Headers`, and fails silently without it

`new Redirect(status, location)` validates the location with
`new Headers({ location })` inside a `try`/`catch` that rethrows as "Invalid
redirect location". With no `Headers` global the `ReferenceError` is caught by
that same handler, so a perfectly good redirect is reported as a malformed one.
The polyfill in the adapter now carries a small `Headers`; it exists to be
constructed, and nothing in the engine sends a request.

## A remote function's refusal has to arrive as kit's own control object

The `$app/server` shim used to throw `new Error(message)` with a `status`
property. Nothing downstream reads that: `handle_error` classifies by
`instanceof HttpError`, and `transformError` decides whether to swallow or
rethrow by `instanceof Redirect`. A redirect thrown by a query during a render
was therefore rendered as an error page instead of answering the document with a
3xx. The shim now throws kit's `HttpError` and `Redirect`, and Go's answer
envelope grew an `r` arm to say which.

## The dev leg of the suite is broken on this branch, and was before this step

`vp dev` renders pages with kit's *own* server runtime, which calls the
generated `.remote.ts` stub in process — the stub that throws. So every page in
dev arrives with its remote boundaries showing `Internal Error`, and kit's own
`transformError` answers the document with 500. `GET http://localhost:5173/`
returns 500 with `session-failed` and `site-failed` in the markup.

`just e2e dev` against `vp dev` + the proxy fails 39 of the first 42 scenarios,
starting with `app.feature`'s first one and including every feature — it is not
an `ssr.feature` problem.

This is what moving `<SignIn />` out of its pending boundary (slice 1) did to the
proxied path, not anything the error branch changed: the failures are kit's dev
SSR running stubs, and no skgo code is involved. Whatever the fix is — telling
kit's dev server not to server-render, or pointing the dev `$app/server` at Go —
it is its own piece of work.
