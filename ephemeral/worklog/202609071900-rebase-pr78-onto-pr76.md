## The conflict git didn't flag

`internal/ssr/ssr.go` and `internal/ssr/ssr_test.go` auto-merged with no
`<<<<<<<` markers — but the result didn't compile. `#78` changed
`Engine.Render`'s third parameter from a bare `Host` (a func type, nilable)
to a `Hosts` struct (`{Remote, Fetch, Match}`). `#76`'s and `#77`'s test
additions in `ssr_test.go` predated that change and called `Render(...,
nil)` or `Render(..., someHostFunc)` — both invalid once the parameter type
is a struct. Git's line-based merge had no way to see this: the hunks
didn't overlap textually, only semantically. Fixed by wrapping the four
affected call sites in `ssr.Hosts{Remote: ...}` / `ssr.Hosts{}`.

Lesson: a clean `git merge-tree` (no conflict markers) is not proof the
result compiles when two branches independently touch a shared function's
call sites and one of them also changes that function's signature. Always
`go build`/`go vet` immediately after a rebase completes, even when no file
showed a textual conflict.
