# Sprint 004: server loads

oracle: **kit's own dev server is the specification, running.** Authoring a
throwaway `src/routes/probe/` with hand-written `+layout.server.ts` /
`+page.server.ts` and curling `/probe/__data.json` through the dev proxy
produced the real bytes for every case — layout+page composition, `uses`,
promises and their chunks, `error()`, `redirect()`, the unmatched path, the
`x-sveltekit-invalidated` positions — in about ten minutes, before a line of Go
was written. Every golden string in `data_test.go` came from there. Do this
first for any mirrored feature; source reading is for *why*, not for *what the
bytes are*.

correction: `+page.server.go` is not a legal Go file name. `go build` refuses
`+` outright ("invalid input file name"). The Go files are `page.server.go` and
`layout.server.go`, and the file name is what decides which stub they generate.

trap: both of those live in the **same directory**, so Go compiles them as one
package and they cannot both declare `func load`. The generator therefore has
to record the marked function's own name; emitting a hardcoded `load` compiles
for a route with only one of the two and breaks on the first route with both.

correction: the manifest's node table cannot be built from `builder.routes`.
`RouteDefinition` carries no layout/leaf indices. Two public Builder APIs do
carry them: `generateManifest()` (the routes' `page.{layouts,errors,leaf}`) and
`getServerDirectory()/nodes/<n>.js`, whose `export const server_id = "..."` is
the only place the mapping from a branch slot back to an authored
`+*.server.ts` survives the build. Do not regex `generateManifest()`'s text —
its only imports sit inside lazy thunks, so writing it to a file and
`import()`ing it yields the real object and runs no application code.

trap (this one silently serves stale data): kit's `aborted` flag looks like a
race in Go and is not one in JavaScript. Kit starts every wanted node in the
same tick, so none of them can observe a flag a sibling's failure sets later;
only the extra runs `parent()` drives can. A literal Go port with goroutines
lets a fast-failing leaf mark the layout `{"type":"skip"}` — and `skip` does not
mean "no data", it means "client, reuse what you have", which on a cold load is
nothing. The fix is to exempt the nodes the client actually asked for from the
check. Symptom before the fix: `/account/statement` returned the layout as
`skip` about half the time.

trap: `{"type":"skip"}` is also why a skipped node's load may still have to
*run*. `parent()` calls the memoised function directly, past the invalidation
gate, so a page that reads its parent forces the layout to execute — and the
layout's result must still not be serialised. Both halves are load-bearing and
the browser proves it: navigating back to `/account` runs the layout on the
server (serial goes up) while the page keeps showing the old number, because
the client reused its retained node.

note: a Go map's key order is not kit's. `uses` and the `{status, message}`
error node both came out alphabetised until they were given ordered types.
Harmless to kit's client, which `JSON.parse`s either way, but it makes the
output diffable against kit's, which is worth more.

note: `skgo.Deferred[T]` cannot go through polytype — there is no Go type it
could project to `Promise<T>` — so a load's result is projected property by
property into an inline TypeScript object type instead of being declared as a
named one. Named types *inside* the properties are still polytype's. The
serializer only substitutes deferred values at the top level of the returned
object, and the generator refuses one nested deeper rather than letting it
serialise as `null`.

process: mutation-tested the suite, five mutations, each failing exactly the
scenario that claims the behaviour and nothing else — guard removed (3
scenarios), `x-sveltekit-invalidated` ignored (the layout-reuse scenario),
chunks never sent (the streaming scenario), `Parent` returning nothing (the
composition scenario), a failing load made to succeed (the error scenario).

defect (not this sprint's): `skgo generate` still writes polytype output into
whatever module owns a type on the wire, so a remote function returning
`skgo.None` would generate files inside the skgo library itself. The survey's
gap report already records it; the loads work did not make it worse and did not
fix it.
