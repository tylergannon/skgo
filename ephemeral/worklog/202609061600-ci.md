# CI — traps, and one thing this repository cannot do

## A conflicting pull request gets no `pull_request` run at all

Measured, and it cost an hour of looking for a disabled-Actions setting. PR #28
was opened while `main` had moved; `gh api .../actions/runs` reported
`total_count: 0` and `.../actions/workflows` was empty, which reads exactly like
a repository where Actions has never been switched on. Actions was on. GitHub
runs the `pull_request` event against a merge commit, and when the merge
conflicts there is nothing to run it against, so it creates no run and no check —
silence, not a red.

That is the worst possible failure mode for a regression detector: the branch
that most needs a signal is the one that gets none. The workflow therefore
triggers on `push`, which always fires, and on `pull_request` only for forks
(whose pushes this repository never sees). One run per commit, no duplicates,
no blind spot.

## Branch protection is not available on this repository

`tylergannon/skgo` is private on a free plan. Both
`repos/.../branches/main/protection` and `repos/.../rulesets` answer

    403 Upgrade to GitHub Pro or make this repository public to enable this feature

So a red run is visible on the pull request and nothing mechanically stops it
being merged. That needs the repository made public, or a paid plan.

## `pnpm` is the one tool nothing in the repository pins

`mise x -- pnpm` makes pnpm look pinned. It is not: pnpm is in neither
`example/mise.toml` nor `web/node_modules/.bin`, and on the machine this was
written on it comes from Homebrew. CI installs 11.25.0 explicitly, matching
`devEngines` in `example/e2e/package.json`. If that drifts from whatever wrote
the lockfile, the runner and the developer are running different package
managers and nothing says so.

## `vp dev` forks, so the pid `&` reports does not hold the port

Measured: the launcher was pid 73440, the socket on 5422 belonged to 73453.
`kill $!` leaves vite listening; the next bind then fails and, because the port
is still answering, the browser suite tests the *previous* server and passes.
Anything that starts `vp dev` has to stop it by port, and has to wait for the
port to actually come free — `kill -9` returns before the socket does.

## The dev-mode run is not implied by the prod-mode run

Prod serves bytes embedded in the binary; dev has kit's own dev server render
the document while Go proxies to it, and that is where the remote-function
registries have to win over kit's throwing stub. `ORIGIN` for the dev run is the
**Go** origin, not vite's: kit fixes the app's origin into the client at build
time and the browser only ever talks to Go. Both were run locally, 27 scenarios
each, before any of this was pushed.

## Running the browser suite rewrites tracked screenshots

`ephemeral/screenshots/loads/<mode>/` and several files beside it are tracked,
and the suite overwrites them on every run. A local run therefore dirties the
tree with a dozen modified PNGs that belong to somebody else's sprint. Discard
them rather than committing them; on a runner nothing commits, so it only bites
by hand.

## `lsof` exits 1 when *any* selector matched nothing, while still printing pids

The trap that nearly shipped a guard that could not see. `lsof -t -i tcp:8080`
with something on 8080 exits 0. `lsof -t -i tcp:8080 -i tcp:5173` with the same
process on 8080 and nothing on 5173 prints `95285` and exits **1**. So

    if lsof -t -i tcp:"$A" -i tcp:"$B" >/dev/null 2>&1; then echo "busy"; fi

is false precisely in the ordinary case — one port taken, one free — which is
the only case the check exists for. Test the *output*, never the status:

    bound=$(lsof -t -i tcp:"$A" -i tcp:"$B" 2>/dev/null || true)
    [ -n "$bound" ] && ...

## `vp dev` binds the name `localhost`, so a 127.0.0.1 proxy target reaches nothing

`just dev` runs bare `vp dev`, which binds `localhost` rather than an address.
On macOS that resolves to `::1` first, and the result is silent and confusing:
vite prints `Local: http://localhost:5173/` and looks completely healthy, while
`curl http://127.0.0.1:5173/` gets connection refused and a Go server started
with `-proxy http://127.0.0.1:5173` proxies to nothing.

Address it as `localhost` — the name vite itself prints — in both the readiness
wait and `--proxy`, and a runner and a laptop behave the same way. The scaffold
template sidesteps this by passing `--host 127.0.0.1 --port 5173 --strictPort`
(`internal/newapp/template/mise.toml.tmpl`); the `dev` recipe does not, and this
branch does not own the Justfile.

## Waiting on an open socket is not waiting on a server

The first version waited with bash's `/dev/tcp`. A bound socket is not an
answered request, and — see above — it is also the wrong question when the
server bound a different address family. Every wait here is `curl -sf` against
a real URL, so "ready" means the thing the browser is about to do worked once.

## `X-Skgo-Mode` is checked against a word written into the workflow

The dev leg's real risk is not a crash, it is a server that quietly serves the
embedded build: every scenario then passes, twice, and the proxied path is
never exercised at all. Each leg reads the header and compares it to the literal
`prod`/`dev` in the step, not to anything the run reported earlier.

## A command's own return value is asserted by nothing, in Go or in the browser

Found while choosing a breakage CI could catch. `Rename` was changed to store
the new text and hand back the row as it was — a stale response, the classic
shape of this bug — and it was invisible: `go vet`, both modules' tests and the
scaffold test all passed, and so did 27 scenarios in each mode.

It is invisible because it is not observable. `TodoDetail.svelte` renders
`(await getTodo(id)).text` and renames with `.updates(getTodo(id))`, so the
single flight carries a re-run of the *query* and the command's own return
value is never displayed. `addTodo` is the same shape. Whatever those two
commands answer with, nothing in this repository looks at it.

Not a hole in the suite — the browser cannot see what the browser is never
shown — but worth knowing before someone writes a scenario they believe covers
it.

## The breakage CI did catch

`Store.Add` recording the todo's id and not its text. Every Go check stays
green: `store_test.go` calls `Add` only to move the counts, and no Go test
asserts the text a todo comes back with. The browser fails two scenarios in
each mode, and the frame shows what a person would see — a healthy page,
`Todos: 3`, and a third row that is an empty bullet.

That is the shape worth reaching for in a breakage proof: not a bug the unit
tests already own, but one that is only visible to something looking at the
page.
