# Published v0.46.0 consumer verification

discovery: /opt/homebrew/bin/skgo on this machine was an un-brewed dev build (v0.45.2-0.20261031220649-c0083fc7d389, placed 2026-10-31) and the tylergannon/skgo tap was not tapped, so "brew reinstall --cask" from CLAUDE.md could not run as written. -> copied the dev build to the session scratchpad (`backup/skgo-dev-c0083fc7`), tapped, `brew install --cask tylergannon/skgo/skgo`; the cask binary digests identically to the GitHub Release tarball's `skgo`.
decision: Consumer runs use the published executables extracted from the GitHub Release tarballs (v0.45.1 for the "existing" consumer, v0.46.0 for fresh creation) at scratchpad paths, never the checkout build. `skgo update` replaces the executable it runs from, so running it from the scratchpad copy keeps the Homebrew install and the user's PATH untouched.
friction: Both released CLIs require VitePlus exactly 1.3.0 and `update --complete-version` would run `vp upgrade 1.3.0` against a global vp that reports another version; the global vp is 1.4.0. -> PATH shim dir with `vp -> ~/.vite-plus/1.3.0/bin/vp` for `skgo new`, and `--vp` pointing at the same binary for `skgo update`, so the user's global vp is not downgraded.
friction: Two `skgo new` runs started at the same time (v0.46.0 fresh46 and v0.45.1 app45) and the second failed inside `sv add @skgo/sv@0.45.1` with "Failed to download community add-on packages … Unexpected end of input"; the published 0.45.1 tarball matches the registry integrity and parses, and the same command re-run alone succeeded. -> create consumers serially; a shared-download collision is the hypothesis, not an established cause (round-01 review).
discovery: Both published CLIs let vp pick `sv@1.2.0` for `sv create`/`sv add` (the 3.1.0 journal qualified sv 1.1.1); creation and the add-on worked with 1.2.0.
discovery: `skgo update` rewrites web/package.json through its own `pinDependencies`: keys sorted, `packageManager: pnpm@12.14.0` added, an empty `dependencies` object added and `devEngines.packageManager.onFail` set to "error", while a fresh v0.46.0 scaffold keeps `onFail: "download"` and no `packageManager`. Authored scripts and dependencies survive (update_test.go:172 covers this); recorded as a shape divergence between fresh and updated apps, not a defect.
correction: Round-01 review: `GOPRIVATE=github.com/tylergannon/*` (set with `go env -w` on this machine) implies `GONOPROXY` as well as `GONOSUMDB`, so the first update's `go get` fetched tag v0.46.0 straight from GitHub (`cache/vcs` in the scoped cache), and `@v/*.info/.zip` files prove nothing about transport because Go writes them for direct fetches too. -> Repeated the update from the archived pre-update app with an empty cache and `GOPROXY=https://proxy.golang.org` (no `direct`), `GONOPROXY=none GOPRIVATE=none GONOSUMDB=none`; an empty `GOPRIVATE=` does not override a `go env -w` value, `none` does. Rule: capture effective `go env` in the log and prove transport by the absence of `cache/vcs` plus the sumdb lookup record, never by cache file names.
friction: In this tool's zsh, `env $ENV cmd` does not word-split `$ENV`; the whole string became `GOPROXY` and `go get` failed with "invalid character in host name". -> write explicit `VAR=value` assignments.
friction: `go tool skgo check` on a fresh published-v0.46.0 app reports `staticcheck` incomplete ("export data version 5 is greater than maximum supported version 4"): `skgo check` takes whatever `staticcheck` PATH has, and this machine's `~/go/bin/staticcheck` is v0.8.1 built with go1.27.1. -> reinstall staticcheck with the current Go; skgo could name the staticcheck build's Go version in the diagnostic.
doc_bug: `svelte-format` fails on every fresh scaffold ("project Prettier and prettier-plugin-svelte are required") because sv's minimal template ships no Prettier; already deferred in the Kit 3.1.1 worklog, still true on the published CLI.
decision: Browser evidence for the updated consumer came from the Playwright MCP (Chromium) against the standalone binary on a session-owned port: one navigation entry, client-side `/notes`, `/_app/remote/o0aeqp/getNotes` 200, zero console messages. Servers were started and stopped by pid; no other app was touched.
decision: The native-shell example (`plugins/native-shell/example`) is not advanced to v0.46.0: its README pairs it with the core version its native artifact targets (v0.41.0/adapter 0.40.1), so a release of this core alone does not move it.
