# Fix plan for SKGo #265

The development server must eventually serve the settled bytes on disk after a real edit, including a rapid restoration of previously served contents. Metadata-only touches must remain invisible to invalidation. Intermediate states of an unfinished save may coalesce.

## Basis and proposed change

Research at `9c5c614` exercised the actual isolated `vp dev` server. Three rapid restores with macOS's native `fs.watch` backend were rejected by the patched chokidar 3.6.0 bundled in vite-plus-core 1.0.0; Vite served `probe = 2` 300 ms after the file on disk returned to `probe = 1`. The 150 ms control passed. Independent literal assertions failed without `awaitWriteFinish` and passed with a 50 ms stability threshold and 10 ms poll interval. This is not Linux, browser HMR, or Go rendering qualification. See issue #265 and `ephemeral/research/watcher-265/`.

The user prioritizes build success and stable observation over a modest latency increase. Start implementation qualification with an adapter-wide default for `server.watch.awaitWriteFinish` in the existing `gojaDevUnchangedFiles` Vite plugin: `{ stabilityThreshold: 200, pollInterval: 25 }`. These are proposed values, not yet demonstrated by the research. Qualify increases up to 400 ms if they improve partial-save or platform reliability; do not select the smallest passing value merely for speed. The initial ceiling of 400 ms remains below the existing fixture's 500/700 ms write spacing and roughly one-second quiet wait. Before exceeding it, amend the fixture's quiet waits and separated-write phases to derive from the configured stability threshold and poll interval, then repeat qualification and review. Compare candidate values with the same scripted save patterns and focused contracts at `-count=3`. Require a reproducible failing save or platform condition at the smaller value that the larger value resolves; absent demonstrated benefit, keep 200/25. Record the selected values and captured evidence without claiming statistical reliability from three repetitions; no unchecked escalation is allowed. This uses chokidar's supported pending-write path, which emits after stability and precedes its lossy 50 ms change throttle. Keep the byte digest filter and existing generated-output exclusions. The default belongs in the adapter so ordinary SKGo apps benefit; an example-only configuration would leave users exposed.

Vite merges plugin config returns as overrides. In the adapter config hook, read the incoming `config.server?.watch?.awaitWriteFinish` and contribute the new value only when it is `undefined`; omit the option otherwise. Preserve explicit `false`, `true`, and configured objects unchanged, alongside the existing ignored-output contribution. Explicit `false` opts out and retains chokidar behavior; the default restored-content guarantee applies to ordinary configuration. Kit already replaces `server.watch: null` with its own ignored-output object before the adapter post plugin runs, so restoring that lost intent is outside this fix. Do not add a contract pretending the adapter can preserve information Kit erased. Do not patch private `_throttle` internals or add another filesystem watcher. The earlier 50/10 research remains comparison evidence only. Validate the selected larger values against all preservation cases; a longer interval cannot by itself guarantee correctness for every unfinished save.

At 200/25, a quiet edit ordinarily incurs roughly 200–225 ms of added watcher latency, plus scheduling and processing time. This is an accepted stabilization cost, not a hard deadline or an end-to-end performance claim. Validate the chosen default on native macOS FSEvents as well as native `fs.watch` and explicit polling; each uses the pending-write path, and only the forced `fs.watch` backend has candidate evidence so far.

## Implementation and regression

1. Add a small config contract in the adapter's ordinary Go tests showing that the resolved watcher receives the default while explicit `false`, `true`, configured objects, and output exclusions survive. Exercise real Vite resolution with command `serve` (the plugin uses `apply: "serve"`), rather than merely comparing the plugin's returned object.
2. Extend the existing `TestMain` copy setup to write a fixture-only Vite config wrapper: rename the copied original config to `fixture-base.ts` (not a config discovery name), import it from the wrapper at `vite.config.ts`, and merge test configuration plus a small fixture plugin. The package-wide fixture will explicitly use `useFsEvents:false,usePolling:false` on macOS and Linux. All its contracts thereby share one `vp dev` and exercise native `fs.watch`; this change is confined to the temporary copy. The fixture plugin may record event timing and provide a one-shot synchronization barrier for filesystem edits. It must not replace throttle outcomes or synthesize the filesystem notifications the regression is meant to prove. Provide a test-only mode that leaves native watcher options untouched, and another that selects polling, for targeted qualification of the new default on those backends; they are preservation runs, while negative mutation proof belongs to `fs.watch`. The copied config and its imported base are startup fixtures, not edited during tests: Vite tracks both as config dependencies and would restart the server if either changed. No extra long-lived server or production research endpoint is needed.
3. Make the rapid-restore research into a permanent Go regression in that fixture. Use actual filesystem writes and HTTP module reads with literal original and edited markers. First wait for the first change-log entry to be delivered and for the edited module to be served, then immediately restore the original. Assert the exact restored disk bytes, the final Vite response, and the second delivered change-log entry. Separately exercise a page/component fixture rendered through `example.NewHandler` from original to edited to restored literal markers, covering Go's module-cache invalidation. Keep Go rendering outside the rapid module trial's timing-critical sequence so render latency cannot produce a misleading passing baseline. Each edit counted separately was already delivered before the next write; unfinished unobserved edits may coalesce. Keep any backend selection or synchronization instrumentation confined to the copied test fixture; production must not acquire research endpoints.
4. Make the regression load-bearing in an independent mutation run with the new default removed. Observe chokidar's public `raw` event for the filesystem witness and `change` for the first delivery. Match the resolved fixture-file path and take the earliest matching raw notification after the restore write; the file and directory watchers can both report it; do not alter dispatch or private throttle methods. Only this mutation qualification on native `fs.watch` requires a restore witness inside 50 ms of the first delivery. Attempt at most five trials; out-of-window trials cannot count as broken-baseline proof. If no in-window trial is obtained, report the mutation qualification as inconclusive and unmet, not as product success or the expected failing baseline. The independent validator must see an in-window trial and the actual restored-content assertion fail without the default. Restore the default and verify that restored contents become observable. In ordinary CI runs and native/polling preservation runs, every trial asserts settled restored disk bytes, Vite response, and change-log entries regardless of whether the event was inside 50 ms. Log the timing but do not fail a working product for a missed witness; FSEvents and polling cannot be expected to satisfy this timing window. Keep Go document qualification separate from the race-sensitive module sequence. Do not assume HTTP is fast enough or stretch the throttle window. Final-state assertions should retry until a bounded deadline instead of sleeping 300 ms and declaring success. A timeout is failure and must print the served markers and event timing. Do not require one event for every unobserved intermediate write.
5. Repair the existing template guard to recognize the pinned Kit 3.0.0 error it actually throws: `error.name === "SvelteKit error"`, the `app_template_tag_missing` code on the first message line, and the expected authored-file/missing-tag body. Include the sibling `app_template_missing` error for that authored template, so a temporarily absent template during replacement also reports an error and recovers rather than terminating the same watcher. Test both narrowly classified errors and propagation of unrelated exceptions. Kit's message includes a backticked tag and documentation URL; the current one-line equality cannot match it and can let the watcher exception terminate `vp dev`. Continue propagating unrelated exceptions. Re-anchor the existing EventEmitter test by obtaining the thrown error from Kit's installed `src/messages/build-errors.js` helper by absolute file URL (the internal file is not a package export), rather than having the fixture invent the legacy message. This is a narrow prerequisite for the actual partial-save recovery contract, not a broad error-handling rewrite.
6. Retain and run the existing real-server assertions for metadata-only touches, distinct invalid UTF-8 changes, generated output exclusion, and source edits; run the template partial-save recovery contract. Add a real-server partial-save assertion: exercise an incomplete template write completed inside the configured quiet window (coalesced save) and one held beyond the configured threshold and poll interval until the actual Kit `app_template_tag_missing` error is observed in the emitted error message/log while `vp dev` remains alive (delivered partial save). In each path first observe a literal before marker, then complete the save to a valid template with a different literal after marker: assert the served document contains after and excludes before. Returning to identical pre-test bytes would make the coalesced-save assertion pass with a silenced watcher, so that is not this contract. Include a temporarily absent-template replacement held until its actual error is observed, followed by a completed template with a new marker. All three must leave the server alive and serve the new complete template; these are distinct paths. Express their timing relative to the selected threshold, not unrelated magic sleeps. The EventEmitter contract bypasses chokidar and cannot prove this stability path; merely observing no error overlay would also be insufficient. Verify same-size replacements because this example's `probe = 1` and `probe = 2` have equal byte lengths.

## Validation and delivery

An independent agent removes the new default and runs the rapid-restore contract to establish a failing baseline, restores it and verifies correct restored responses, then exercises the preservation cases. The independent macOS validator must run three focused invocations: forced native `fs.watch`, native default FSEvents, and explicit polling. Each invocation covers restored module and Go-document contents plus the preservation cases, and records the command, tested SHA, actual `watcher.options`, and results in PR/#265 evidence. These are mandatory per-change qualification runs, not a claim that Linux CI provides recurring macOS coverage. Any backend disagreement blocks delivery until explained and repaired. Run the contracts on actual Linux CI too; macOS with forced `fs.watch` remains a reproduction tool, not Linux qualification. Use the existing CI workflow rather than a second acceptance runner. Run the repository's required build, vet, and `just test` once for the final implementation. If browser HMR remains a claimed result, demonstrate a page updating to the changed marker and back in development mode without forcing navigation; otherwise state that boundary clearly.

Use `/consensus` with Claude to review the final implementation and its proof against #265 and repository instructions. Address material findings and re-review in the same session until no material findings remain. Update #265 and the PR with observable results, the tested SHA, Linux results, and material limits. Squash-merge only after the restored-content contract and preservation cases pass; then synchronize the root checkout and clean up the implementation worktree. This document is a plan; it changes no production behavior.
