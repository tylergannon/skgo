# Build the new SKGO dev server

## The plan in brief

Start from **`dev` at `b2f2c00483139b821072a94d22875674909e9eaf`**, where [PR #322](https://github.com/tylergannon/skgo/pull/322) completed the deletion requested in #321. Build one new Go dev server from the indexed upstream implementations. The old server and failed branch supply no implementation foundation or compatibility requirements.

`dev` is the temporary integration branch for deletion and the entire replacement. Worktree branches and replacement PRs target `dev`; incomplete checkpoints are allowed there without publishing releases. Production checks still mean what they say, and unavailable development qualification stays explicitly unavailable until restored. Promote the finished replacement to `main` only after the complete validation below. This plan does not require incomplete development functionality to remain releaseable at each checkpoint.

The engineering order is:

1. Establish generated code replacement through real SKGO handlers, including stable function identity, ordinary bodies, host state and lifetime.
2. Establish retained, event-fed source and build inputs shared by generation and compilation.
3. Restore development rendering using Vite's actual environment/ModuleRunner lifecycle in pooled goja.
4. Connect those capabilities into ordinary `skgo dev`, from save through application installation to Kit refresh.
5. Complete the structural-edit, error, dependency, stream and process-lifecycle behavior.
6. Remove remaining unnecessary work and qualify the complete developer experience.

These are implementation missions with accepted behaviors and dependency boundaries, not optional product modes. Step 1's bounded retained native checkpoint is qualified; its remaining work is ordered below, starting with cgo removal. Steps 2 and 3 are independent of its implementation and can proceed alongside it under separate ownership; step 4 requires all three. Steps 1–3 can be built and tested without advertising a usable dev server. The integrated replacement is delivered when steps 4–6 satisfy the complete behavior below. No old server remains available during reconstruction.

**Next recommended build:** keep the working native implementation, remove its cgo requirement, and qualify the unchanged generated-handler contract on native Mac ARM64 and Linux AMD64. Then demonstrate selective reclamation alongside compatible retained values. Removing cgo improves build requirements; bounded retention broadens eligible edits; reclamation extends editing sessions before a state-resetting host replacement. These are separate benefits and separate checkpoints, not one expanding build.

## Product and process

### One owner of the save-to-browser transition

The session is a long-running Go program owning the public socket, project state, build work, diagnostics and every process it starts. It starts Vite through the project's VitePlus environment and a Go application host. The application host owns its initialized application state, code replacement and the mandatory goja renderer pool. Vite owns frontend compilation, its environment graphs and frontend HMR. Kit's own client owns query/load invalidation and navigation.

Keeping the application host separate from the session lets a structural application rebuild replace the host without losing the public listener, project state or Vite. Compatible Go edits replace code inside the host without restarting it. These are two installation operations owned by the same new session. There is no server-selection switch or compatibility path.

**Browser/Vite topology:** Go owns the public listener and the browser's single public origin, matching Kit's configured `paths.origin`. The private loopback Vite listener supplies tooling, module transformation, configured assets and HMR, with application fallthrough directed to Go and no reachable Node application handler. Preserve the pinned Kit/Vite middleware precedence: Kit's asset middleware, Vite's tooling/transform/raw-filesystem handling, Kit's removal of early static/public middleware, and its deliberate reuse of the saved static responder for existing allowed project files and after an application 404. Removing Kit's application handler must preserve the tooling portions around it, including base-path handling, the service-worker entry response and Chrome-devtools special requests where supported by Kit. A blanket “HTML means Go” rule or a manifest allowlist cannot reproduce that precedence. Once application routing is selected, Go answers documents, loads, remotes, actions and endpoints. Step 3 owns the private tooling/fallthrough boundary; step 4 owns its composition with Go's public listener, standard HTTP reverse-proxy/upgrade facilities and application responses. Vite advertises the public origin/WebSocket endpoint through configuration supported by the actual installed pin.

Suppressing Kit's request handler also removes its first validating manifest pass. Step 3 preserves Kit's frontend matcher-module/export/name validation during tooling metadata preparation: importing the frontend matcher module in Node is tooling validation, never server request matching or Go endpoint execution. Step 2 preserves SKGO's existing paired Go declarations and typed-registry validation. Validate before publishing a route/registry revision. A failed revision remains a visible development diagnostic; repair clears it through the ordinary update path.

Production continues to use the existing production generator, Go handlers, adapter build and pooled goja renderer. Application I/O executes in Go. The development loader and its platform requirements do not enter a production build.

### What a save does

The desired source revision, installed application revision and Vite environment lifecycle are distinct facts. They must not be represented by one ambiguous “ready” flag.

1. A watcher reports paths. The project owner reads changed bytes/membership and advances desired source state. Equal-content noise does not advance it. Configuration or workspace changes invalidate their corresponding view.
2. gopls-derived metadata and dependency rules determine affected analysis and generators. The Go compiler has its own dependency/artifact identity; a generation cache hit does not establish executable freshness.
3. Work consumes captured inputs associated with that revision. Compatible work is shared; obsolete work is canceled where cancellation is supported. Later completion of canceled work cannot admit outputs, errors or code.
4. Generation prepares owned outputs. Compilation produces either a compatible set of compiled replacement objects or a complete application candidate. Compatibility is explicit: source-shape changes, unsupported lifetimes and missing integration are different outcomes.
5. The session verifies the candidate still serves desired source and the relevant Vite lifecycle. The host prepares installation; generated frontend outputs and Kit graph changes are coordinated before announcing readiness. Publication never means “the compile process exited.”
6. After installation, the session sends an ordered readiness event through Vite. Kit refreshes active Go queries/loads. Frontend-only edits continue through Vite's ordinary HMR.

The publication boundary must account for externally visible generation writes. An epoch check after files have already escaped into Vite is too late. Existing generation staging/output ownership is adapted to prepare/cancel/commit semantics; it is not replaced with a new project-copying framework.

Requests use an installed application. They do not walk source, hash the project or wait behind ordinary compile work. Initial failure has a diagnostic response; a later compiler failure keeps the successful application installed and makes current failure visible in the terminal/browser. Repair installs the corrected revision and clears that diagnostic.

### Code replacement and state

The current implementation uses `pkujhd/goloader` over stock released Go compiler output. Its retained generated bridge is qualified on **Go 1.27.2 darwin/arm64 and linux/amd64**. The maintained development profile still requires cgo; removing that requirement is the next bounded build above, with experimental Mac evidence and Linux execution still pending. Production is already independent of the development loader and remains cgo-free.

The host, replacement objects, dependency archives and private compiler-source view must use the same selected toolchain and compatible build settings. Derive its identity from the toolchain the session actually runs. A toolchain change requires rebuilding those artifacts; reject mismatches before loading. At startup, unsupported platforms or Go series and missing prerequisites of the actual qualified profile refuse the dev server with an actionable diagnostic before advertising readiness. After cgo removal, absent cgo or a C compiler is not a missing prerequisite. There is no old-server or restart-only fallback product. GoLoader's minor-version support claims do not prove every patch, but another 1.27 patch is not rejected merely for differing from the initial test version. Support claims require the real-host tests.

Step 1 selects the initial CI toolchain explicitly and keeps these host tests running on both target platforms thereafter. The existing selected Swift/client tests on macOS do not provide that coverage. Do not raise library/workspace minimum Go directives just to select CI's toolchain or change the scaffold's existing policy of recording its running Go version. Preparation uses a private source view; installed Go remains untouched.

Adopt the stable named-function dispatch pattern found in got-reload, adapted to compiler-produced Go code rather than its interpreter. A generated host entry keeps the original Go function identity; installation changes the implementation reached through it. Generated bindings and function references used by `skgo.Refresh` must agree on that identity. Normal production generation keeps its direct Go calls.

**Build isolation:** Step 1 owns producing the development host as well as its dispatch. Development-transformed Go source, registrations, loader dependencies and compiler/package-access preparation live in a private development build view. They never replace the authored tree's ordinary generated Go files or modify its module declarations. The session automatically builds that profile as part of the single dev server. The CLI and normal SDK test binary do not statically depend on the loader. After any development session, ordinary `go generate` and `CGO_ENABLED=0 go build` still consume the direct production bindings without a cleanup/regeneration ritual. The code replacement fixture tests explicitly exercise that transition.

The host owns package initialization, existing types and mutable state. Body replacement must not rerun initializers, instantiate a second copy of a package's mutable globals, or give values crossing the boundary incompatible Go type identity. Calls through helpers must execute the intended revision too; replacing only the registered entry while silently calling an outdated helper fails the capability.

An edited helper invalidates its complete executable caller closure, including possible inlined copies. Admit code replacement only when every affected caller can be replaced consistently through the code replacement boundary. A helper with an uninstrumented host/background caller, or a closure the implementation cannot establish, requires a complete application rebuild. No partial code update may leave two callers observing different revisions of the edited helper. Analysis typerefs are not this executable caller proof.

This fixes the integration contract, not a new public API. Further work extends the qualified generated implementation, mapping the relevant upstream rewrite/registration and loader symbol/data/type/initialization handling at the affected seam. Blind whole-package loading is not justified: GoLoader loads initialization tasks, and its symbol map distinguishes host data and locally loaded text. Historical manual preflights do not replace the generated implementation or its tests.

The initial code replacement contract is useful synchronous body edits with unchanged declarations, using arguments, existing structs, a helper and initialized state. Cover a remote with arguments, a server load returning an existing struct, and a normal endpoint/action body. Function/signature/type/package-state/initialization changes use complete rebuilding until separately supported. Unchanged signatures alone do not establish replacement compatibility. Method edits outside replaceable dispatch, missing host package storage, incompatible named-type identity and executable candidate initialization require rebuilding before load; a bare initialization-task record is not itself executable initialization. For compatible synchronous edits, closures, boxed values and retained candidate-backed data may select bounded module retention instead of rebuilding. New asynchronous execution remains a scope exclusion until separately supported. Do not invent a generic deep copier or general escape analysis to increase reclamation coverage.

Code publication must keep executing code and data backed by loaded objects alive until the actual consumer finishes, including the module handle's Go-owned backing allocations. A lease ending when a load returns is insufficient if SSR/serialization still uses its result. Ownership begins before entry into candidate code and follows the actual executor and consumer, including a live/deferred producer that outlives its HTTP handler whenever that execution is admitted. Nested execution and consumption preserve one coherent revision. Reclaim only revisions within the demonstrated retirement boundary after their consumers finish; retain other compatible revisions within explicit mapping/count budgets. This replaces the earlier mandatory current-plus-candidate rule. A partially failed runtime load is not a normal compile error: preserve the last desired source, replace the uncertain host through the same session, and explain that recovery. Do not call `Unload` on code or metadata that may remain reachable.

Nested generated calls/internal fetches borrow their enclosing loaded-code lifetime; they must not recursively acquire a writer-preferring lock and deadlock a pending publication. Unrelated host-only live streams do not hold a blanket code-publication lease. A compatible revision that cannot drain within the bound falls back to retention charged against the budget, rather than immediately resetting application state. Budget exhaustion or an uncertain host selects host replacement; structural or unsupported edits still use complete rebuilding. Host shutdown itself has bounded drain/cancellation. Repeated saves never justify unmapping reachable code or accumulating unlimited loaded revisions.
