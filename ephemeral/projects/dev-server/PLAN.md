# Build the new SKGO dev server

## The plan in brief

Start from **`dev` at `b2f2c00483139b821072a94d22875674909e9eaf`**, where [PR #322](https://github.com/tylergannon/skgo/pull/322) completed the deletion requested in #321. Build one new Go dev server from the indexed upstream implementations. The old server and failed branch supply no implementation foundation or compatibility requirements.

`dev` is the temporary integration branch for deletion and the entire replacement. Worktree branches and replacement PRs target `dev`; incomplete checkpoints are allowed there without publishing releases. Production checks still mean what they say, and unavailable development qualification stays explicitly unavailable until restored. Promote the finished replacement to `main` only after the complete validation below. This plan does not require incomplete development functionality to remain releaseable at each checkpoint.

The engineering order is:

1. Establish generated code replacement through real SKGO handlers, including stable function identity, ordinary bodies, host state and lifetime.
2. Establish retained, event-fed source and build inputs shared by generation and compilation.
3. Restore development rendering using Vite's actual environment/ModuleRunner lifecycle in pooled goja.
4. Connect those capabilities into ordinary `skgo dev`, from save through application installation to Kit refresh.
5. Complete the structural-edit, error, dependency, stream and process-lifecycle behavior.
6. Remove remaining unnecessary work and qualify the complete developer experience.

These are implementation missions with accepted behaviors and dependency boundaries, not optional product modes. GoLoader integration is the first priority and risk to resolve. Steps 2 and 3 are independent of its implementation and can proceed alongside it under separate ownership; step 4 requires all three. Steps 1–3 can be built and tested without advertising a usable dev server. The integrated replacement is delivered when steps 4–6 satisfy the complete behavior below. No old server remains available during reconstruction.

## Product and process

### One owner of the save-to-browser transition

The session is a long-running Go program owning the public socket, project state, build work, diagnostics and every process it starts. It starts Vite through the project's VitePlus environment and a Go application host. The application host owns its initialized application state, code replacement and the mandatory goja renderer pool. Vite owns frontend compilation, its environment graphs and frontend HMR. Kit's own client owns query/load invalidation and navigation.

Keeping the application host separate from the session lets a structural application rebuild replace the host without losing the public listener, project state or Vite. Compatible Go edits replace code inside the host without restarting it. These are two installation operations owned by the same new session. There is no server-selection switch or compatibility path.

**Browser/Vite topology:** Go owns the public listener and the browser's single public origin, matching Kit's configured `paths.origin`. The private loopback Vite listener supplies tooling, module transformation, configured assets and HMR, with application fallthrough directed to Go and no reachable Node application handler. Preserve the pinned Kit/Vite middleware precedence: Kit's asset middleware, Vite's tooling/transform/raw-filesystem handling, Kit's removal of early static/public middleware, and its deliberate reuse of the saved static responder for existing allowed project files and after an application 404. Removing Kit's application handler must preserve the tooling portions around it, including base-path handling, the service-worker entry response and Chrome-devtools special requests where supported by Kit. A blanket “HTML means Go” rule or a manifest allowlist cannot reproduce that precedence. Once application routing is selected, Go answers documents, loads, remotes, actions and endpoints. Step 3 owns the private tooling/fallthrough boundary; step 4 owns its composition with Go's public listener, standard HTTP reverse-proxy/upgrade facilities and application responses. Vite advertises the public origin/WebSocket endpoint through configuration supported by the actual installed pin.

Suppressing Kit's request handler also removes its first validating manifest pass. Step 3 preserves Kit's frontend matcher-module/export/name validation during tooling metadata preparation; step 2 preserves SKGO's existing paired Go declarations and typed-registry validation. Validate before publishing a route/registry revision, without using Node for server request matching. A failed revision remains a visible development diagnostic; repair clears it through the ordinary update path.

Production continues to use the existing production generator, Go handlers, adapter build and pooled goja renderer. Application I/O executes in Go. The development loader and its platform requirements do not enter a production build.

### What a save does

The desired source revision, installed application revision and Vite environment lifecycle are distinct facts. They must not be represented by one ambiguous “ready” flag.

1. A watcher reports paths. The project owner reads changed bytes/membership and advances desired source state. Equal-content noise does not advance it. Configuration or workspace changes invalidate their corresponding view.
2. gopls-derived metadata and dependency rules determine affected analysis and generators. The Go compiler has its own dependency/artifact identity; a generation cache hit does not establish executable freshness.
3. Work consumes captured inputs associated with that revision. Compatible work is shared; obsolete work is canceled where cancellation is supported. Later completion of canceled work cannot admit outputs, errors or code.
4. Generation prepares owned outputs. Compilation produces either a compatible set of compiled replacement objects or a complete application candidate. Compatibility is explicit: source-shape changes, unsupported lifetimes and missing integration are different outcomes.
5. The session verifies the candidate still serves desired source and the relevant Vite lifecycle. The host prepares installation; generated frontend outputs and Kit graph changes are coordinated before announcing readiness. Publication never means “the compile process exited.”
6. After installation, the session sends an ordered readiness event through Vite. Kit refreshes active Go queries/loads. Frontend-only edits continue through Vite's ordinary HMR.

The publication boundary must account for externally visible generation writes. An epoch check after files have already escaped into Vite is too late. Existing generation staging/output ownership is adapted to prepare/cancel/commit semantics; it is not replaced with a new project-copying framework.

Requests use an installed application. They do not walk source, hash the project or wait behind ordinary compile work. Initial failure has a diagnostic response; a later compiler failure keeps the successful application installed and makes current failure visible in the terminal/browser. Repair installs the corrected revision and clears that diagnostic.

### Code replacement and state

Use the selected `pkujhd/goloader` over stock released Go compiler output. Step 1's code replacement primitive must pass on **Go 1.27.2 darwin/arm64 and linux/amd64** before its exit condition is met. Start local development on this Mac, and qualify the same primitive on Ubuntu as part of that task, not only after integration. Both loader profiles require cgo (Linux also uses its cgo `libdl`/`-ldl` code). Step 1 owns aligning CI's selected toolchain and the automated private development preparation to Go 1.27.2: current `go-version-file` declarations select 1.27.1 and are not sufficient. It also establishes continuing CI qualification of the same real-host code replacement tests on darwin/arm64 and linux/amd64 for subsequent replacement changes; the existing macOS job's selected Swift/client tests do not provide this coverage. The runner must actually match the claimed architecture. Preparing importable object packages uses a private source view of that selected stock toolchain; installed Go remains untouched. Other unsupported configurations produce a startup diagnostic instead of silently losing code replacement; production's platform boundary remains independent.

Adopt the stable named-function dispatch pattern found in got-reload, adapted to compiler-produced Go code rather than its interpreter. A generated host entry keeps the original Go function identity; installation changes the implementation reached through it. Generated bindings and function references used by `skgo.Refresh` must agree on that identity. Normal production generation keeps its direct Go calls.

**Build isolation:** Step 1 owns producing the development host as well as its dispatch. Development-transformed Go source, registrations, loader dependencies and compiler/package-access preparation live in a private development build view. They never replace the authored tree's ordinary generated Go files or modify its module declarations. The session automatically builds that profile as part of the single dev server. The CLI and normal SDK test binary do not statically depend on the loader. After any development session, ordinary `go generate` and `CGO_ENABLED=0 go build` still consume the direct production bindings without a cleanup/regeneration ritual. The code replacement fixture tests explicitly exercise that transition.

The host owns package initialization, existing types and mutable state. Body replacement must not rerun initializers, instantiate a second copy of a package's mutable globals, or give values crossing the boundary incompatible Go type identity. Calls through helpers must execute the intended revision too; replacing only the registered entry while silently calling an outdated helper fails the capability.

An edited helper invalidates its complete executable caller closure, including possible inlined copies. Admit code replacement only when every affected caller can be replaced consistently through the code replacement boundary. A helper with an uninstrumented host/background caller, or a closure the implementation cannot establish, requires a complete application rebuild. No partial code update may leave two callers observing different revisions of the edited helper. Analysis typerefs are not this executable caller proof.

This fixes the integration contract, not a new public API. The implementer maps got-reload's rewrite/registration code, GoLoader's symbol/data/type/initialization handling and SKGO's generated typed calls before selecting the smallest implementation. Blind whole-package loading is not justified: GoLoader loads initialization tasks, and its symbol map distinguishes host data and locally loaded text. The manual preflight's host anchor is evidence, not the generated implementation.

The initial code replacement contract is useful synchronous body edits with unchanged declarations, using arguments, existing structs, a helper and initialized state. Cover a remote with arguments, a server load returning an existing struct, and a normal endpoint/action body. Function/signature/type/package-state/initialization changes use complete rebuilding until separately supported. Changes involving newly loaded callbacks, goroutines, deferred values, runtime types **or data that can escape into retained host state** are not admitted merely because the source still has the same signature. Primitive host-state mutation such as the fixture counter is allowed; persisting strings, slices, interfaces/errors or composite values is classified for rebuilding unless the generated boundary establishes host ownership by a demonstrated copy/encoding before retirement. Calls into APIs that may retain candidate-backed values are included in that rule. Do not invent a generic deep copier or assume GoLoader makes every literal safe. These edits remain functional through complete rebuilding; broader code replacement compatibility requires its corresponding lifetime proof.

Code publication must keep executing code and data backed by loaded objects alive until the actual consumer finishes. A lease ending when a load returns is insufficient if SSR/serialization still uses its result. The first implementation uses the POC's bounded current-plus-candidate publication discipline for admitted synchronous work, extended through real handler/serialization ownership. It must reject unsupported escaping loaded-code lifetime before load. A partially failed runtime load is not a normal compile error: preserve the last desired source, replace the uncertain host through the same session, and explain that recovery. Do not call `Unload` on code or metadata that may remain reachable.

Nested generated calls/internal fetches borrow their enclosing loaded-code lifetime; they must not recursively acquire a writer-preferring lock and deadlock a pending publication. Unrelated host-only live streams do not hold a blanket code-publication lease. Coalesce pending edits while retirement is blocked, and use explicit bounded drain/cancellation or application-host replacement when execution cannot retire. Repeated saves never justify unmapping reachable code or accumulating unlimited loaded revisions.

### 1. Generated code replacement at the real application boundary

**Mission:** A freshly generated application's ordinary Go handlers can use compiled replacement bodies while its host identity/state and Kit behavior remain correct.

**Ownership:** Go compilation/loading, development-only generated dispatch and its integration with the surviving typed production registries. This owner also owns the compatibility result and loaded-code lifetime boundary. It does not own a file watcher, CLI server, browser notification system or new compiler.

This ownership includes the private dev build view and development dependency isolation described above. The Go test driver builds/launches a separate real application host with the prepared stock Go 1.27.2 environment and symbols explicitly retained (`-ldflags=-s=false` at that pin), then drives that host's actual HTTP handler. It does not load Go objects into a normally stripped `go test` executable. Preparation is automated by the tested build primitive on both darwin/arm64 and linux/amd64, including cgo/libdl prerequisites and private object-package access. Prepare the private toolchain view and host once per test binary and reuse them across its assertions; reuse preparation across runs only under a key covering the toolchain identity and preparation inputs, and rebuild hosts when their source/dependency inputs change. Missing prerequisites fail rather than skip. Align CI's selected Go version here; root `just test` stays an ordinary Go test invocation and exercises code replacement through the real host on Ubuntu. The same host tests also run in the darwin/arm64 CI lane from this step onward, including after integration; passing locally once does not qualify later changes on that platform. Development-host-only code is isolated so the ordinary SDK/CLI build does not require the private GOROOT. Incomplete work can remain on `dev`, but step 1 is not marked passed by a Mac-only run.

**Accepted proof, in Go tests at the composed handler:**

- Given argument 7, counter initialized to 40 and helper `2*x`, the first `helper(x)+counter.Add(1)` call returns literal 55. Add 10 in the registered body: the next call returns 66. Change the helper to `3*x`: the next call returns 74. PID and initializer count remain fixed. The generated boundary must also handle an existing application struct and private package state; a new manually supplied counter argument cannot stand in for ordinary application state.
- Two generated handlers share that helper: both observe its changed calculation after a code update, including when one caller's source bytes are unchanged. Add a caller outside the code replacement boundary and assert the helper edit is classified for a complete rebuild before any partial code installation; step 5 proves that rebuild reaches every caller.
- A load returns an existing application struct; its rendered HTTP document contains the new field value. An endpoint/action body changes a real response. These use generated integration, not fixture-specific manual dispatch.
- A command using `skgo.Refresh` or `RefreshNoArg` resolves the original named query after multiple swaps. Typed errors, cookies and generated codecs still cross the real boundary correctly.
- Hold a call/serialization across publication. Its old revision stays valid through consumption; the next call reaches the new one. Repeat swaps with forced GC and verify retirement independently, including data actually backed by loaded-object mappings where copying is claimed.
- Hold a nested internal request/helper while a writer waits; it completes without reentrant-lock deadlock. An unrelated live stream does not prevent a compatible synchronous handler update.
- A compiler failure leaves the previous result and state intact; repair installs the new result. A type/global-initializer/new escaping-lifetime change is classified before an unsafe load. The test distinguishes unsupported edit from missing dispatch or loader setup.
- A body that persists a candidate-derived string/slice/error/composite into host state is either rejected for code replacement before load, or its proved host-owned representation survives retirement and GC. Test genuinely candidate-backed data where that is the claimed hazard; a literal GoLoader already copied to heap cannot establish the general claim.
- In the same generated project, run the dev profile, stop it, and build/run production with cgo disabled without restoring or regenerating source. Production returns its supplied fixture value and contains no development-loader dependency.

Use the selected loader/preflight rather than repeating engine selection. The first-priority engineering task is mapping and implementing this generated bridge, including private symbols, host state/types and initializer behavior. Steps 2–3 have independent owners and may progress alongside it; integrated steps 4–6 depend on this contract passing. If a source incompatibility prevents the useful code replacement contract, stop dependent work and bring the exact failing case and smallest proposed adaptation to the user; stop all replacement work if the overall goal is shown impossible, as requested. The deliverable does not silently become restart-only, literal-only, a different loader, or restored old code. Only a new user decision can change the goal, in which case revise steps 4–6 and their acceptance before executing that changed scope. There is no pre-authorized weaker contingent product.

**Exit condition:** The generated bridge and its load-bearing real-host tests pass with stock Go 1.27.2 on darwin/arm64 and linux/amd64, with production build isolation demonstrated. There is still no advertised dev server. This is an application primitive, not product completion.

### 2. Retained project inputs, selective generation and compiler inputs

**Mission:** Each observed source change updates retained state; affected generation and compilation for code replacement or a full application consume the same selected bytes.

**Ownership:** Project/file state and shared analysis/generation. Adapt existing production source-view/output staging in its current owner; coordinate necessary polytype work in its own worktree. The GoLoader integration owner consumes compilation inputs from this boundary and retains the host's actual dependency artifacts.

**Accepted proof:**

- Watch a real temporary application, including a local replacement and embed directory. Atomic editor saves, preserved-mtime writes, populated-directory creation and rename/removal lead to fixture-defined generated/served values without request-triggered discovery. A reported event forces acquisition of fresh changed-file content; gopls's disk-cache mtime shortcut is not evidence that an observed equal-mtime save is unchanged.
- Hold generation and compiler work, save another fixture, and release the held work in either order. Only current source may publish its generated output or candidate. Diagnostic locations refer to the authored file/revision that caused them.
- A body-only edit reuses generation but compiles the new body. Struct/tag/constant/marker changes regenerate exactly the affected outputs; generated output writes do not trigger an endless self-build loop. Removed producers remove only their own artifacts.
- Compiler imports come from archives associated with the host build and current dependency identities. Editing a local dependency or adding an embed match invalidates executable eligibility even when a type projection stays the same.
- Existing Go matcher support stays load-bearing: a route `[n=Order]`, fixture metadata naming `Order` and paired Go `Order(string) (OrderNumber, bool)` produce the named Go value at the handler. Missing Go functions and wrong Go signatures prevent publication with the corresponding diagnostic. Repair resumes matching, including pages without loads and endpoint fallback. Step 3 independently proves frontend export/name validation; step 4's client navigation confirms Kit and Go select the same installed fixture route.
- A routine edit reads the changed/affected closure rather than recapturing all authored source. Unchanged analyses remain available across edits and recover after an invalid intermediate source.

**Exit condition:** The event-to-candidate path produces real current inputs for code replacement or a full build with bounded retained state. Avoid a separate persistent Go compiler or generic revision platform. Compilation remains stock Go's responsibility.

### 3. Vite-driven development documents in Go

**Mission:** A Go handler renders live Kit pages from a Vite environment, and both SSR and frontend HMR follow Vite's real module lifecycle.

**Ownership:** Necessary adapter/client glue, upstream ModuleRunner/goja integration, private Vite routing guard and live Kit metadata. This owner does not implement application compilation or a second filesystem watcher for Vite-owned modules.

Begin with one bounded direct-use compatibility test of Vite's actual runner in a pooled goja runtime, using its custom evaluator/transport seams. Bundle the upstream dependency through the existing adapter build, with source-map interception/debug/transport timers disabled or owned in Go, external module execution rejected, and every I/O operation in Go. This is reuse of an upstream library, not authorization to write an SKGO JavaScript runner or add application I/O/timers to the engine. If direct use needs unsupported engine semantics or prohibited custom JavaScript/runtime behavior, record that exact blocker and implement the necessary algorithms in Go. Run the same alias/cycle/cache/update tests on the selected integration. Do not assume direct use works or prescribe a maintained port before this check.

**Accepted proof:** Module alias/cycle/shared-evaluation tests follow upstream cases. A changed dependency with unchanged importer bytes updates the next SSR document; deletion/recreation and changed import edges recover. Vite cache/invalidate replies and reconnect/reset behavior work. Real Kit branch/node/template/style data, Go I/O callbacks and renderer-pool reentrancy work through the handler.

**Render consistency decision:** A request holds its selected manifest/registry and exclusive ownership of its checked-out runtime. Ordered environment updates apply at runtime admission, not by polling a private file journal during requests. A render whose required module fetch crosses an invalidated environment must not emit a mixed document: discard/retry before commitment. A post-commit stream that cannot continue consistently is canceled and recovered through the update lifecycle. Already evaluated old code can finish while held; an absent historical module cannot be fetched from current Vite and passed off as old. This policy is tested with an update while a Go-backed async render and a dynamic import are held. A manifest refcount by itself does not solve this problem.

The retry applies to module preparation/rendering, not replaying a submitted command, action or HTML form. Retain the request's resolved Go answers/action result through render preparation. If a consistent response cannot be completed after application effects, surface the controlled failure without automatically executing those effects again. Hold an action across an environment edit and assert its fixture-owned mutation happened exactly once.

**Exit condition:** Live Go-rendered documents and Vite HMR work together without the deleted runner, old HTTP journal, old SSR refresh locks or raw watcher interception. At the private Vite listener, real module, CSS, asset and HMR requests obey pinned Kit/Vite rules. An existing allowed project file, including the fixture's `/package.json`, receives its fixture bytes through the retained static responder; denied files obey Vite's access rules. Requests requiring application responses produce explicit fallthrough and cannot execute Kit's Node application handler. Test static/route collisions, configured base/assets behavior and manifest-validation failure/repair at this boundary, including missing frontend matcher exports and route-required names. These tests require no public Go listener. Any new synchronization follows the tested render-consistency boundary. The production pool/renderer remains production infrastructure.
